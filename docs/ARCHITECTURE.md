### Crate responsibilities

| Crate | Purpose | Talks to |
|---|---|---|
| `divora-core` | All non-Tauri-coupled audio logic: capture/output streams (Phase 2), DSP effect trait + implementations (Phase 3+), preset model (Phase 4), soundboard mixer (Phase 5), virtual mic detection (Phase 6). Unit-testable without a UI. | The OS audio APIs (via `cpal`), the filesystem (presets, soundboard cache) |
| `divora-app` | Tauri shell. Owns the IPC surface, lifecycle, window. Bridges UI events to `divora-core` and pushes engine state back. | `divora-core`, Tauri runtime, frontend |
| `src/` (frontend) | SolidJS UI. App shell, design system, effect controls, preset picker, soundboard grid, settings, device picker, first-run wizard. | Tauri commands via `@tauri-apps/api/core` |

The crate name `divora-app` is internal; the user-visible product name is **DivoraVoice** (set via `tauri.conf.json` `productName`).

### Threading (planned, materializes in Phase 2)

- **Audio callback thread** — driven by `cpal`. Real-time. Zero allocations. Reads input, writes input ring buffer, reads output ring buffer, writes output device.
- **DSP worker thread** — high priority, not real-time. Runs the effect chain + soundboard mixer. Owns mutable DSP state.
- **UI / IPC thread** — Tauri main. Owns presets, settings, device list. Pushes preset changes to the DSP thread via atomic pointer swap.

State across threads:
- Whole-chain swap: atomic pointer to an immutable `Arc<EffectChain>`.
- Per-parameter sweeps: `AtomicF32`/`AtomicU32`.
- Audio samples: `ringbuf` SPSC.

### Internal audio format

- 48 kHz, mono, `f32` samples internally.
- Boundary resampling via `rubato` to match device rates.
- Internal buffer: 256 samples (~5.3 ms at 48 kHz).

### Audio engine architecture

The `AudioEngine` owns a dedicated OS thread (`divora-audio`) that hosts
the cpal streams (which are `!Send`). The Tauri main thread talks to it
through an `mpsc` channel; shared state is an `Arc<EngineState>` with
atomic fields so the UI thread can read levels / monitor / running flag
without locking.

Each cpal callback is **alloc-free**: a stack array up to
`MAX_FRAMES_PER_CALLBACK` (4096 mono samples) absorbs the buffer,
samples flow through a `ringbuf::HeapRb<f32>` SPSC ring buffer between
the input and output callbacks (`RING_BUFFER_FRAMES = 8192` ≈ 170 ms at
48 kHz). The output callback fans the mono signal across the device's
output channels, or writes silence when `monitor` is false.

```
Mic device  -> input callback  -> mono mixdown -> SPSC ring buf
                                      |                  |
                                      v                  v
                              LevelMeter (IN)    output callback
                                                       |
                                                       v
                                  LevelMeter (OUT) -> speaker / headphones
```

#### Constraints (Phase 2 only — relaxed in later phases)

- Sample format: F32 only on both devices. Non-F32 fails with a clear
  `AudioEngineError::UnsupportedSampleFormat`.
- Sample rates must match. `AudioEngineError::SampleRateMismatch` fires
  if not. Resampling via `rubato` lands in Phase 8 polish.
- Internal channel layout: mono. Mixdown is straight sum / channel count.

### DSP architecture

- `EffectChain` is owned by the audio output callback. No locks; no contention with the UI thread.
- The UI sends `DspCommand`s, which `AudioEngine::send_dsp` lowers into `DspEdit`s **on the calling thread** — that is where a chain is built and a voice-model load is started. They travel a bounded SPSC channel, recreated on every engine start, that the callback drains at the top of each buffer.
- `EffectChain::apply(edit)` is the single mutation point, and no **structural** edit through it allocates or frees: a `ReplaceChain` swaps in an already-built chain and **returns** the one it displaced (as does `Clear`), for the per-session graveyard thread to drop. `SetParam` / `SetEnabled` mutate in place.
- The reactive-modulation queue beside it works the same way and for the same reason — with the reactive panel on it is on the preset-switch path too, since a config goes out on every preset switch and every input event of a targeted slider (with the panel off the config is constant and the frontend dedupes it away). It is bounded, and `ReactiveModulator::configure` **swaps** the route tables rather than copying, so the config leaves through the graveyard carrying the table it displaced.
- One free remains **in the drain**: `SetParam` drops the owned key string it was sent, once per slider tick. `divora-core/tests/rt_chain_swap_allocations.rs` asserts it at exactly one — that test drives the real drain functions, not copies of them, and pins the zeros for everything else.
- The soundboard drain takes the same route now: `SoundboardMixer::apply` returns what it retired — a displaced voice's name and decoded clip, or a `Stop`'s own owned name — and the callback pushes it to the graveyard. `play` uses `mem::replace` rather than `*v = Voice { .. }`, which is where the free was: an idle slot still owns an `Arc`, a stopped slot still owns its clip, and when the callback holds a clip's last reference, stealing that slot freed the whole buffer there (measured 3 frees for a 1.9 MB clip, one of them the 1.9 MB). `apply` is `#[must_use]`, and because that only catches an *accidental* discard, a source-level test also pins that the callback routes the value rather than dropping it.
- **`VoiceConvert` inference is the remaining architectural violation.** It runs in the audio callback, and `ort` allocates tensors on every call. Through v1.56.0 it was a deadline problem too: the downsampler ran whole 4096-sample rounds, so each round handed the bundled *streaming* model (208-sample chunks) about twenty inferences to run back to back in one callback — with `the_bundled_model_in_the_callback`, 78 of 2 000 callbacks at 480 frames took **101–115 ms** against a 10 ms budget, one a round (an earlier production-path run saw 23 of 600 at 83–106 ms). Both resamplers now convert all the input each callback brings (`resample_rounds`), so inferences come one at a time as the audio arrives: at 480 frames about three callbacks in four run one, of about 5 ms, and none of 2 000 went over budget in three runs (worst 7.8–9.4 ms, mean 4.0–4.3 ms; the converter alone, nothing else in the chain, test profile). At 256 frames (a 5.33 ms budget) one inference does not fit: 500–696 of 3 750 went over, by up to 3.5 ms. A non-streaming model still makes its one 4096-sample call in a single callback (v1.51.1 measured `run_inference` at 14–16 ms). Taking inference off the callback still means its own thread behind a latency-compensating queue; that is deliberately unfixed and deliberately stated, and no CI test reaches inference because CI has no ONNX runtime. v1.51.2 moved the resamplers' construction off the thread and pinned it; the phases around inference, priming included, allocate nothing (`the_phases_around_inference_allocate_nothing`).
- Engine restarts (Stop → Start) clear the chain; the frontend re-sends `SetChain` via a `createEffect` on `(presetId, engineRunning)`.

### A/B compare flow

```
ui.ab = "A"
chains[presetId]  = live A chain (writable by Inspector + ChainCards)
abSlots[presetId] = { A: snapshot, B: snapshot }

user clicks "B" segmented:
  abSlots[presetId].A := clone(chain())   // snapshot the live edits
  chains[presetId]    := clone(abSlots[presetId].B)
  ui.ab               := "B"
  SetChain(spec)                          // fresh chain to audio thread

user clicks "A":
  abSlots[presetId].B := clone(chain())
  chains[presetId]    := clone(abSlots[presetId].A)
  ui.ab               := "A"
  SetChain(spec)
```

Picking a different preset (`usePreset(id)`) resets `abSlots[id]` to two copies of the new chain and sets `ui.ab` back to A.

### Audio pipeline (Phase 5)

```
mic device ──► input callback ──► mono ring buffer ──┐
                                                     ▼
                                       output callback drains:
                                       1. dsp_rx (effect-chain edits)
                                       2. sb_rx  (play/stop/panic)
                                       3. consumer.pop_slice(&mut mono)
                                       4. chain.process(&mut mono, sr)        ← mic with effects
                                       5. soundboard.mix_into(&mut mono, sr)  ← + clips
                                       6. fan-out to device channels
```

Effects apply only to the voice. Soundboard clips play at their natural amplitude; if they distort the user can reduce levels at the clip source. The virtual-mic routing in Phase 6 will see the combined `mono` so call participants hear *both* the modulated voice and the soundboard.

### Sample-rate handling

Each `Voice` holds the clip's native sample rate. During `mix_into(engine_rate)` the read position advances by `clip_rate / engine_rate` per output sample and adjacent samples are linearly interpolated. This handles common mismatches (44.1 kHz clip on a 48 kHz device) without chipmunking, at the cost of mild aliasing. A proper resampler (rubato) is a future polish job.

### Voice pool

| Field | Purpose |
|---|---|
| `MAX_VOICES = 16` | Hard cap on simultaneous voices |
| `play` | Find an idle voice; if none, steal the one with the lowest `started_at` |
| `stop(clip_id)` | Deactivate every voice with matching id |
| `stop_all` | Mark every voice idle |
| `mix_into(output, engine_rate)` | Add every active voice's interpolated sample to `output`; auto-deactivate at end-of-buffer |
| `snapshot(engine_rate)` | Build a `Vec<PlayingClipSnapshot>` for the UI |

### Cache + commands

The Tauri shell owns the decoded-clip cache (`Mutex<HashMap<String, DecodedClip>>` on `AppState`). `play_soundboard_clip(clipId, path)`:

1. Locks the cache.
2. If `clip_id` is present, clones the `DecodedClip` (cheap — `Arc<Vec<f32>>`) and returns.
3. Otherwise calls `decode_clip(path)`, inserts, returns.
4. Forwards `SoundboardCommand::Play { clip_id, samples, sample_rate }` to the engine.

Subsequent plays of the same clip do zero file I/O.

### VB-Cable detection

Detection is pure name-matching against the cpal device lists — we never open the cable, never poke at the registry. Both heuristics fire case-insensitively:

```
looks_like_cable_input(name)  := "cable input"  ⊂ name  OR  ("vb-audio" ⊂ name AND "input"  ⊂ name)
looks_like_cable_output(name) := "cable output" ⊂ name  OR  ("vb-audio" ⊂ name AND "output" ⊂ name)
```

This recognises:
- Canonical `CABLE Input (VB-Audio Virtual Cable)` / `CABLE Output (…)`
- `VB-Audio Hi-Fi Cable Input` / `VB-Audio Voicemeeter VAIO3 Output`

And rejects unrelated devices (`Blue Yeti X`, `HyperX Cloud II`, `Realtek HD Audio`, etc.).

`detect_virtual_mic()` returns `VirtualMicStatus { detected, cableInputDevice, cableOutputDevice, downloadUrl }` where `detected` is the conjunction of both fields being `Some`. The download URL (`https://vb-audio.com/Cable/`) is a hard-coded `&'static str` — never user-overridable, never fetched from the network.

### Global hotkey architecture

`tauri-plugin-global-shortcut` registers OS-wide hotkeys per Tauri window. The plugin's handler receives `(app_handle, shortcut, event)` and our wrapper looks up the registered id by reverse-mapping `shortcuts: Mutex<HashMap<String, Shortcut>>`, then emits a Tauri event with the canonical payload:

```rust
GlobalShortcutEvent { id, accelerator, state }  // state: "pressed" | "released"
```

Each shortcut id is stable application-defined (`ptm` / `panic` / `monitor` / `mute`, the reserved prefixes `sb:`, `rec:`, `replay:`, `overlay:` and `mute:`); the accelerator is whatever string the user picked (`Space`, `Ctrl+Shift+P`, etc.). The frontend subscribes once in `App.tsx` `onMount` and routes by id in `dispatchGlobalShortcut`, the one JavaScript path every id takes — also while the window is hidden to the tray. Two ids are acted on in Rust before they get there, when the press arrives inside `WM_HOTKEY`; `global_shortcut_handler` still emits both events afterwards:

- **`overlay:arrange`** (v1.55.0): the handler hands every event to `overlay_windows::hotkey`, and a press switches the open overlay between Arrange and Locked (see "Stream overlay window"). Its JavaScript branch never calls `set_overlay_mode`, which would toggle the press twice.
- **`mute`** (v1.56.0): the handler then hands every event to `mute_on_hotkey`, and a press — never a release (`hotkey_mute_request`) — calls `engine.toggle_input_muted()`, one atomic operation on the engine's mute (see "Mute (v1.56.0)"). The page plays no part, so it doesn't matter whether it is hidden, reloading or busy, and two quick presses are two flips. global-hotkey 0.8.0 registers every key with `MOD_NOREPEAT`, so a held key doesn't repeat. Its JavaScript branch does nothing: acting there would flip it twice. The page learns the new state from the next `audio-levels` tick.

The routes:

```
event.id         | event.state | action
-----------------|-------------|-------------------------------
"ptm"            | "pressed"   | setUi("pressed", true)
"ptm"            | "released"  | setUi("pressed", false)
"panic"          | "pressed"   | panicSoundboard()
"monitor"        | "pressed"   | toggleMonitor()
"rec:screen"     | "pressed"   | toggleScreenRecording()   (v1.52.0)
"rec:wav"        | "pressed"   | toggleRecording()         (v1.52.0)
"replay:save"    | "pressed"   | saveReplay()              (v1.54.0)
"replay:toggle"  | "pressed"   | toggleReplay() — refused with a toast
                 |             | until Replay has been turned on from
                 |             | the card once                (v1.54.0)
"overlay:arrange"| "pressed"   | noteOverlayHotkey() — a toast only, while
                 |             | the overlay is off or starting; the
                 |             | backend already toggled the mode
                 |             | (global_shortcut_handler →
                 |             | overlay_windows::hotkey)     (v1.55.0)
"mute"           | "pressed"   | nothing — the backend already flipped
                 |             | the mute (global_shortcut_handler →
                 |             | mute_on_hotkey)              (v1.56.0)

```

`syncHotkeyBindings()` is called once after subscribe; it re-registers every persisted accelerator so a Windows restart doesn't lose the bindings (Tauri's plugin loses its registrations when the process exits).

**Persistence (v1.51.4).**

- **What is saved:** every action in `HOTKEY_ACTIONS` (`src/data/hotkeys.ts`), in `divora.hotkeyBindings`: the `ptm` / `panic` / `monitor` bindings (v1.51.4), `rec:screen` and `rec:wav` (v1.52.0), `replay:save` and `replay:toggle` (v1.54.0), `overlay:arrange` (v1.55.0) and `mute` (v1.56.0). They are read back through `readHotkeyBindings`, which keeps only the known actions and only string values; an action missing from an older save reads as unbound. A bound PTM key also restores `ui.ptmKey` for the in-app listener. Before v1.51.4 the paragraph above was aspirational: these three bindings were held only in memory, so `syncHotkeyBindings()` had nothing to re-register after a restart. Per-tile `sb:` hotkeys were already persisted, in `divora.tileHotkeys`.
- **A refused key leaves the action unbound (v1.56.0).** `register_global_shortcut` takes the action's old shortcut out of the map, and unregisters it, before it parses the new accelerator (`rebind`, tested by `a_refused_key_never_leaves_the_old_one_bound`). Until v1.56.0 the parse came first, so an accelerator the parser refuses — Shift with a digit, captured as "!", the number pad's + ("Ctrl++") or *, a letter outside A to Z — returned early and left the old key live under a binding Settings no longer showed, until a restart or a Clear. The refusal itself is still only logged to the console. **A shared key stays registered (v1.56.0):** Windows keeps one registration per key, so two actions bound to one key share it; `release` returns a key to unregister only when no other action in the map still holds it (`a_shared_key_stays_registered_for_the_other_action`), where until v1.56.0 changing or clearing either action unregistered it and silenced the other. Which of the two a shared key runs is still the handler's first match in the map, which can differ from launch to launch.
- **The Windows key:** the capture component labels it "Win", but the parser behind `register_global_shortcut` (global-hotkey 0.8.0) accepts only `Super` / `Cmd` / `Command`. `keysToAccelerator` and `normalizeAccelerator` turn "Win" into "Super" for every accelerator handed to the backend: the three actions, and soundboard tiles, including ones saved before the fix. `acceleratorToKeys` shows "Super" as "Win" again.

### Why two PTM listeners?

The OS-level hotkey works while the app is unfocused but **does not** swallow the keypress from the focused app. So if a user is typing in Discord with PTM = Space, Discord still gets the spaces. To handle that, `App.tsx` also keeps an in-app `window.addEventListener("keydown")` that triggers the same `ui.pressed` flip when our window has focus AND the event target is `document.body`. Both listeners converge on the same store mutation; the user can't tell which fired.

### Glyph classifier (`src/data/glyphs.ts`)

A deliberately simple geometric classifier — no ML, no template-matching DLLs. Returns `GlyphId | null` (one of triangle / invtriangle / square / circle, or null when the trace is too small / open / unrecognisable).

Pipeline:

```
raw points
  ├─► dedupe              consecutive duplicates removed
  ├─► boundingBox         bail if width < 40 or height < 40
  ├─► resamplePath(48)    uniform arc-length resampling
  ├─► smooth(0)           off by default (natural sampling already smooth enough)
  ├─► endpointGap         classify as "closed" if gap < 0.35 × bbox diagonal
  ├─► turningAngles       cyclic when closed; per-point absolute turn
  └─► findCorners         peaks above ~35°, min separation = N/8, cyclic dedup
```

Decision:

- **0 corners** ⇒ circle
- **4 corners** ⇒ square
- **3 corners** ⇒ triangle vs invtriangle — apex is the corner whose Y is most distant from the median Y of the three corners; apex above the median ⇒ ▲, below ⇒ ▽.
- **anything else** ⇒ null

Tunables live in `CLASSIFIER_DEFAULTS` and are accepted as a partial `config` parameter so tests and future tuning work without forking the module.

### Phase vocoder math (pitch shifter)

```
For each STFT frame at hop H = 256, window N = 1024:

  1. Analysis bin k true frequency:
       expected_advance = 2π · k · H / N
       actual_advance   = phase_now[k] − last_in_phase[k]
       Δ                = wrap_pi(actual_advance − expected_advance)
       true_freq[k]     = (k + Δ · N / (2π · H)) · (sr / N)

  2. Synthesis bin k_out at pitch ratio r = 2^(semitones/12):
       k_src = k_out / r                     (fractional)
       synth_mag[k_out]   = lerp(mag[k_src], mag[k_src+1], frac)
       phase_advance      = (true_freq[k_src] · r) · 2π · H / sr
       synth_phase[k_out] = last_out_phase[k_out] + phase_advance
       last_out_phase[k_out] = synth_phase[k_out]
```

The vocoder maintains its own `last_in_phase` / `last_out_phase` buffers (not the STFT's) so the closure passed to `Stft::process` can mutate them without aliasing the STFT's internal state. Bypass-at-zero-shift means the chain pays zero added latency when the slider is centred.

### Spectrum-warp math (formant shifter)

```
For each STFT frame:

  1. envelope[k]   = mean(mag[k - half .. k + half])     (Hann-style smoother)
  2. excitation[k] = mag[k] / envelope[k]                (clamp env ≥ 1e-6)
  3. warped_env[k] = lerp(envelope[k_src], envelope[k_src+1], frac)
                     where k_src = k / r
  4. new_mag[k]    = warped_env[k] · excitation[k]
```

Phases pass through untouched — formant shifting moves the *shape* of the spectrum, not the per-bin energy across bins. End result: vowel colour darkens / brightens without the fundamental moving.

### Rubato resampler integration

```
                      input_rate = 48 kHz                       output_rate = 44.1 kHz
   ┌──────────┐        ┌──────────────────┐  ┌──────────────────────────┐  ┌──────────┐
   │ Mic      ├───────►│ SPSC ring buffer ├─►│ DSP chain @ input_rate  ├─►│ Resampler│ ──► out
   │ (48 kHz) │        │ (RING_BUFFER_FRAMES)│ │ + Soundboard mix         │  │ (Sinc 128│
   └──────────┘        └──────────────────┘  └──────────────────────────┘  │ tap, B-H │
                                                                            │ window)  │
                                                                            └──────────┘
```

Engine picks `engine_rate = input_rate`. The DSP chain and soundboard mix both run at `engine_rate`. The output callback feeds the chain's mono output into the resampler when needed; if rates match, the resampler is `None` and samples pass through directly.

**One wrapper (v1.51.2).** `dsp::voice_convert` kept a private copy of this wrapper, justified in a comment as avoiding a circular dependency — modules within a crate may reference each other freely, so there was nothing to avoid, and the copy diverged exactly as duplicates do: it kept the fixed-chunk shape and handled the overshoot by discarding it outright. It now uses `MonoResampler`, and its two resamplers are built in `VoiceConverter::new` — i.e. inside `DspEdit::prepare`, on a control thread — rather than lazily from `process`. That moved 1060 allocations, 784 frees and ~0.84 ms out of the audio callback, where a `SetChain` was triggering it after every preset switch, and onto the thread that asked for the switch, taking a chain build with a `VoiceConvert` in it from ~124 µs to ~833 µs.

**Exact fit (v1.51.2).** Each round is sized to the device's own frame count with `Resampler::set_chunk_size`, so one `process` call produces exactly the buffer being filled and nothing is queued between callbacks. `resample_pop` asks the resampler what this buffer needs and pops that much; `resample_render` hands the whole DSP buffer plus a count, so no call site picks a bound. Both are `#[doc(hidden)] pub` for `divora-core/tests/rt_resampler.rs`, whose two-clock harness drives them rather than a copy.

Getting there fixed a badly broken path. A fixed 256-frame chunk against an arbitrary device frame count (480 is the WASAPI shared-mode 10 ms buffer at 48 kHz) overshot on every buffer, and the overshoot was "stashed" by splicing resampler **output** into the **input** queue. The engine also asked for a whole extra chunk every callback, so it demanded more native audio than the input device produces — the ring was permanently empty, the zero-fill ran on 499 of every 500 callbacks, and a third of every block reaching the DSP chain, the recorder, the monitor mix and the voice reading was injected silence. Measured on a 440 Hz tone at 44.1 → 48 kHz with a 480-frame buffer, the tone came out **41 dB below** the noise it was buried in; across the six rate pairs and four buffer sizes the suite covers, the figure ranged from −15 dB to −74 dB. It is now 136–145 dB, and tight across the same grid — the spread collapsing is as much the point as the level.

A small cushion (two rounds, filled once at session start) absorbs the beat between the input device's lump size and the output buffer's — 441 frames arriving every 10 ms against 405 wanted every 9.19 ms, which starves roughly every twelfth callback from an empty ring. The cushion primes and then always serves, which matters only under jitter: with ideal clocks the two designs are indistinguishable (both go silent 2–3 times, all at priming), but with the input device's block size varying by ±120 frames, dropping the latch on every dip measured 9–10 silent buffers over 30 s against 1–2 for priming once. A silent buffer is 10 ms of nothing; serving short instead costs a zero tail of a few frames.

### Latency budget

| Stage | Samples | Time @ 48 kHz |
|---|---|---|
| cpal input buffer | ~256 | 5.3 ms |
| Internal SPSC ring | depends on jitter | ~0–10 ms |
| STFT analysis window | 1024 | 21.3 ms (only when pitch / formant active) |
| Resampler cushion + delay | ~2 rounds + ~64 | ~11 ms (only when rates differ) |
| **Total** | | **~26 ms** (under 30 ms goal) |

The resampler row was "~64 samples, 1.3 ms" until v1.51.2, and that was wrong by four orders of magnitude: the input queue grew without bound — 5.4 s of backlog after 10 s of audio, 32 s after 60 s — so the real figure was unbounded and climbing. The exact-fit rewrite queues nothing; what remains is the priming cushion (two rounds, about 10 ms at 44.1 kHz) plus rubato's own group delay.

### Streaming RNNoise wrapper

```
┌──────────┐      ┌────────────────┐      ┌──────────┐
│  buffer  ├─────►│   in_queue     │      │  output  │
│  (any    │      │  (VecDeque)    │      │  buffer  │
│   size)  │      └───────┬────────┘      └────▲─────┘
└──────────┘              │ when ≥ 480          │
                          ▼                     │
                ┌──────────────────┐            │
                │ DenoiseState     │            │
                │ ::process_frame  │            │
                └────────┬─────────┘            │
                         │                      │
              ┌──────────┴──────────┐           │
              ▼                     ▼           │
        ┌──────────┐         ┌──────────┐       │
        │ out_queue│         │dry_delay │       │
        │(denoised)│         │(matched  │       │
        └────┬─────┘         │  dry)    │       │
             │               └────┬─────┘       │
             └──────────┬─────────┘             │
                        ▼                       │
            mix·wet + (1-mix)·dry  ─────────────┘
            (or silence during warm-up)
```

Per call to `process(buffer, sample_rate)`:

1. **Bypass paths**: if disabled, off-rate, or `mix < 1e-4`, skip the wet pipeline (the `mix=0` path still drains frames so the model stays warm for a later mix change).
2. **Accumulate** every input sample into `in_queue`.
3. **Drain frames** — while `in_queue.len() ≥ 480`, pop a 480-sample frame, scale to int16-range f32, call `DenoiseState::process_frame`, scale back to ±1, push 480 samples each to `out_queue` and `dry_delay`.
4. **Emit** — for each output slot, pop the head of `out_queue` and `dry_delay` and write `mix * wet + (1-mix) * dry`. When the queues are empty (warm-up), emit silence; the dry signal must NOT pass through during warm-up or the wet stream will audibly repeat those samples on the next call.

### Latency + sample rate

- `RNNoise` is locked to **48 kHz**. Off-rate input bypasses the effect (no allocation, no state drift).
- The wet stream lags the input by `FRAME_SIZE - chunk_size` samples — `max(0, 480 − N)` where `N` is the cpal callback size. For a 256-sample callback that's 224 samples of warm-up silence on the very first frame, then steady-state zero added latency per call (the wet output for *frame K* arrives in the same call that fills *frame K*).
- Wet/dry mix is sample-aligned via `dry_delay` so `mix = 0` outputs the dry stream without re-introducing the warm-up delay; the `mix = 0` shortcut just skips writing wet entirely.

### Why `Denoiser` is a separate effect from `Gate`

- `Gate` is a per-sample hysteresis threshold — surgical "shut up when below −52 dB."
- `Denoiser` is a learned model that suppresses spectral content recognised as noise. It works on the actual *texture* of the signal.
- Stacking gate → denoiser at the head of the chain handles both ends: the gate kills the truly-silent moments, and `RNNoise` cleans the spectrum of what's left. Either alone would either over-process (gate too aggressive) or leave audible breath / fan noise through (denoiser alone).

## Phase 12 — AI voice conversion (ONNX / LLVC)

The `VoiceConvert` effect (`divora-core/src/dsp/voice_convert.rs`) runs an
ONNX voice-conversion model over the mic stream via the `ort` crate
(ONNX Runtime). The reference model is **LLVC** (KoeAI, MIT). It is an
ordinary chain effect (`EffectKind::VoiceConvert`) with one extra seam:
`AudioEffect::install` carries the active model as a `Prepared::VoiceModel`
(numbers go through `set_param`; this carries the things that aren't
numbers). `DspCommand::SetResource` is the matching wire command; the
`VoiceModel` is built — and its ONNX load started — on the control thread,
and the model it displaces is handed back for the graveyard thread to drop,
so no session is ever loaded or freed on the audio thread.

**Graceful degradation is the invariant.** When the ONNX runtime DLL or
the model file is missing, or a model's tensor shapes don't match either
supported contract, the effect falls back to **passthrough** — it never
crashes and never hangs. `onnx_runtime_available()` backs the
Settings → Voice library status banner.

Model I/O, the streaming vs non-streaming contracts, how to produce a
model, and the installer-bundling pipeline are documented in detail in
[`voice-models/README.md`](voice-models/README.md). The streaming export
(threaded cache tensors, ~13 ms chunks) lands in v1.3.0; see the
[CHANGELOG](../CHANGELOG.md).

**The hold.** `VoiceConverter` delays the voice by a fixed `hold_frames`: a
whole inference chunk, both resamplers' lookahead (`MonoResampler::LOOKAHEAD`,
64 frames — at 48 kHz for the downsampler, at 16 kHz, so 192 of ours, for the
upsampler), and one 16 kHz sample more, because rubato sums a round's input
need in f32 and rounds it up, and at a chunk's end that one sample is the next
chunk's. That is 883 frames (18.4 ms) for a streaming model and 12 547
(261.4 ms) for a non-streaming one. Both resamplers size every round to what is
queued, so a callback converts all its input bar the lookahead. On engaging,
`run_phases` primes the wet and the dry output queues with the hold's silence,
so every converted sample is ready before its slot comes round at any buffer
size, the delay never moves, and the wet/dry mix lines up. `latency_samples`
reports the same `hold()`, behind the same `engaged` test `process` bypasses
on, so it is 0 whenever the effect passes through — at any rate but 48 kHz too.
Pinned through the real phase order with a copy standing in for inference, at
every buffer size from 1 to 64 and a spread up to 4 096 frames
(`the_voice_comes_out_exactly_the_hold_late_at_any_buffer_size`): the first
sound comes out exactly the hold late, no output sample goes without a
converted one, and over that sweep a hold two frames shorter still never ran
dry while three shorter did. Not counted: the model's own delay — about 5 ms
for the bundled narrator, by an envelope measure that reads the identity
pipeline's hold to within its quarter-millisecond
(`the_bundled_model_in_the_callback`, ignored in CI).

Through v1.56.0 there was no hold and the downsampler ran whole 4096-sample
rounds: fed 480-frame buffers it put out nothing until the 26th, then 4096
samples at once (the 49th at 256 frames). Through the phase order with a
streaming model's chunk, the first converted sample came out 12 000 samples in,
the output then ran dry for about 1 000 more as each round's last partial chunk
waited a further round, and the delay settled at 13 056 samples (272 ms; 277 ms
at 256 frames) while `latency_samples` reported one chunk, 624 (13 ms). With a
non-streaming model it settled at 12 544 against a reported 12 288. The dry
copy was never delayed: until the wet queue first filled, phase 5 popped it and
wrote silence.

## Phase 13 — monitor output routing

A **second, independent cpal output stream** so the main send can go to
VB-Cable (→ Discord / games) while you still hear yourself on
headphones. The main output callback runs the DSP + soundboard mix once
and **taps the processed audio into a monitor ring**; the monitor stream
resamples that to its own device rate and plays it (so the soundboard is
audible on the monitor for free — it's mixed in before the tap).

Gating (`main_output_plays`): with a separate monitor device active, the
**main output always plays** (Discord must keep hearing you) and the
Monitor toggle silences only the headphone stream. With no separate monitor
device, the toggle gates the main output as in Phase 2 — the whole output,
the call included; fully backward-compatible. (Divora's own mute, v1.56.0,
is another thing: it silences your voice on every stream and leaves the
clips playing — see "Mute (v1.56.0)".) The monitor device persists to
`localStorage["divora.monitorDevice"]` and is wired into the live
device-switch effect. `StreamInfo` gains `monitorName`;
`start_audio_engine` + `AudioEngine::start` take a monitor argument.

## Phase 14 — live latency readout

`AudioEffect::latency_samples(sample_rate)` (default 0) reports the
algorithmic delay each effect ADDS while actively processing;
`EffectChain::latency_samples` sums the **enabled** effects (they're
serial). Implemented for the effects that buffer:

| Effect | Added latency |
|---|---|
| Voice Convert | its hold (`hold_frames`): 883 samples (18.4 ms) with a streaming model, 12 547 (261.4 ms) with a non-streaming one — only while it converts (passthrough, or any rate but 48 kHz, adds 0); the model's own delay is not counted |
| Denoiser | one 480-sample RNNoise frame (10 ms) — and only at 48 kHz |
| Pitch / Formant | the phase-vocoder STFT window (1024 samples ≈ 21 ms each) |
| Gate / EQ / Robot / Distortion | 0 (sample-by-sample) |
| Echo / Reverb | 0 to dry-path latency (wet tails) |

The engine publishes the chain's added latency (ms) on the ~30 Hz
`audio-levels` event; the Mixer header shows "· +N ms latency" and moves
live as effects toggle. (The originally-sketched buffer-size selector was
dropped — WASAPI shared mode largely ignores requested buffer sizes.)

## Phase 16 — recording

One-click capture of the post-chain output (voice + soundboard) to a
timestamped 16-bit PCM mono WAV. Recording **reuses the existing
processed-mono tap** (the same signal sent to the main output / VB-Cable),
so a take matches the call audio sample-for-sample. A dedicated **writer
thread** drains a lock-free ring to disk — **no file I/O ever runs on the
real-time callback**. Hot samples clamp to the i16 range (no wrap). Files
land in `%APPDATA%/com.divora.voicemod/recordings/`. Commands:
`start_recording` / `stop_recording` / `recordings_dir`; a `recording`
flag rides the `audio-levels` event. Since v1.56.0, while you're muted the
file has the clips and no voice, as the call does.

### Lifecycle

`OverlayCore`'s phases. Each window has a number, its `instance`, and an input
carrying another window's number changes nothing.

- **Creating(i):** `open_overlay` is building it. A close now is remembered
  and carried out once it is built. A ready handshake that arrives first shows
  it as soon as it is built.
- **Starting(i):** built, hidden, click-through and placed. The watchdog
  (`divora-overlay-watchdog`) gives the page 10 s to say it is ready, then
  destroys the window; the closing statuses carry "The overlay window didn't
  start, so Divora closed it. Try turning it on again.", which main toasts
  once.
- **Shown(i):** the ready handshake arrived and the window was shown.
- **Painted(i):** the page has drawn since it was shown; Arrange is allowed
  (`canArrange`).
- **Closing(i):** after `close_overlay` (`close()`, the path Alt+F4 takes),
  Alt+F4, or the watchdog (`destroy()`). Locked again; no more window state
  is applied to it (`reconcile_plan` is `None`) while it closes.
- **Closed:** after `Destroyed`. Mode, fit and error are reset and the tray
  is refreshed.

Every change goes out as `overlay:status`, the whole `OverlayStatus`, emitted
while the core's lock is held, so statuses leave in the order the state
changed. Every overlay window command returns the same struct, except
`overlay_alive`, which returns nothing.

**The handshake is two app commands, not events.** Right after it broadcasts
`overlay:ready`, the page calls `overlay_handshake {instance, stage: "ready"}`.
Two animation frames after the first status that says its own window is
`shown`, it calls `overlay_handshake {instance, stage: "painted"}`. tauri runs
Rust event listeners under a `try_lock` and parks an event when the lock is
taken (`event/listener.rs`), flushing it only when a later emit runs a Rust
handler. The 30 Hz `audio-levels` emit contends for that lock, and the app has
no other Rust listener, so a parked ready would leave the window hidden until
the watchdog killed it. Commands never take that lock. Ready gates the show;
painted gates Arrange, because a frame can only be seen drawn after the show.
An unpainted Locked window is click-through, so it can't catch clicks. A failed
handshake is logged and retried once.

**Opening again.** `open_overlay` on an open overlay returns its status and
moves nothing. While the last window is still closing it waits up to 2 s for
Closed, then tries once more, else answers "The overlay is still closing. Try
again in a moment."

**Main follows the status.** The controller sets `overlayOpen` from `open`. On
the way to open it attaches geometry tracking (or the fit keeper, when
fitted), and on the way to closed it detaches it. A command's answer can land
after the events that followed it: `close_overlay`'s "closing" arrived about
10 ms after the "closed" event. So main applies a command's answer only if no
`overlay:status` event arrived while the call was on its way (a `heard`
counter); the events carry every change anyway. Found in the real app: without
this rule the Show overlay window toggle stayed on after 6 of 12 quick
open/close cycles. A status with a new `error` is toasted once. The toast
has two tones: success for "Picture added. Use Arrange to place it." and the
hotkey's two notices; error for everything else, the large-picture warning
included. The controller's public actions never reject: a failure they don't
expect is logged with `console.warn`.

**A main-window reload** (F5 / Ctrl+R reload a WebView2 page, and the overlay
window survives it). At start the controller subscribes to `overlay:status`
and `overlay:edit`, reads `overlay_status` and pushes the stored Hide flag,
all at once. It adopts an open overlay from that read unless a status event
arrived first. Adoption treats the status's `error` as already seen, unless
the phase is `closing` (a reload racing the watchdog). Once `overlayOpen` is
true, the state and the scene are pushed again.

**An overlay-page reload:** a ready handshake in Shown or Painted sends the
window back to Shown, so it must paint again before it may arrange, and an
Arrange in progress is locked.

**Closing.** `on_window_event` in `src-tauri/src/lib.rs` still turns
`CloseRequested` into "hide to tray" only for `main`, through
`hides_on_close(label)`. Until v1.51.3 it did this for every window, so the
overlay's `close()` only hid it. The overlay's `CloseRequested` and
`Destroyed` now go to `overlay_windows::on_window_event`. On `CloseRequested`
the `charm` scheme stops serving it and `NonRudeHWND` comes off, then the core
goes to Closing. On `Destroyed` the shell forgets the HWND and its cells, and
the core goes to Closed. The tray's Quit takes `NonRudeHWND` off too
(`before_exit`), because the window then gets no `CloseRequested`.

### Arrange and Locked

The overlay opens **Locked** at every launch: click-through, so clicks reach
whatever is under it. The mode is never saved. **Arrange** takes clicks and
keys so the charms can be moved.

- **Ways in:** Settings' Arrange button, the `overlay:arrange` hotkey, and
  `set_overlay_mode {mode: "arrange" | "toggle"}`. The core accepts only in
  Painted. Otherwise it answers "The overlay is still starting. Try again in a
  moment." or "The overlay isn't open."
- **Ways out:** Esc in the overlay, its Lock button, Settings' Lock button,
  the tray's Lock the overlay (there only while arranging), the hotkey, and
  the lease. `set_overlay_mode {mode: "locked"}` never fails.

**The Arrange lease.** Entering Arrange bumps `arrangeGen`, clears `arranged`,
takes the foreground (below), adds the tray item and starts the lease. The
window stays click-through, and protection stays as it was. Two frames after
the chrome mounts, the page calls `overlay_alive {instance, gen}`, then again
every 500 ms until the chrome unmounts. The first beat of the current
generation sets `arranged` and applies the window: protection off, then
click-through off. Later beats only reset the miss count. No beat sends a
status.
The lease thread (`divora-overlay-lease`) ticks once a second. Three ticks
without a beat lock the overlay as Lock does, with an error main toasts:

- "The overlay didn't respond, so it stayed locked." (it never beat);
- "The overlay stopped responding, so Divora locked it. Turn it off and on
  again if it looks wrong." (it beat, then stopped).

Nothing else would notice a hung or crashed page behind a window that takes
clicks: neither wry nor tauri-runtime-wry handles WebView2's `ProcessFailed`.
A beat's command body runs on a tokio worker, but tauri receives every
command on WebView2's UI thread, which is the main thread, so a main thread
blocked for three ticks ends Arrange just as a silent page does. Beats and
ticks from another instance or generation do nothing.

**Locking** (`lock_edge`): the mode goes back to Locked and the status goes
out at once, while `core` is held. Then, in order, the window is applied
(click-through on, protection last if due), the keyboard is handed back, and
the tray is refreshed. Closing while arranging leaves Arrange too, but only
refreshes the tray: the closing window gets no window state, and the keyboard
isn't handed back.

### Focus

The shell never calls tauri's or tao's `set_focus` on the overlay. When
`SetForegroundWindow` fails, tao's `force_window_active` sends a Left-Alt
press and release with `SendInput` and tries again; in a game that is an
injected Alt key. `the_overlay_never_calls_set_focus` scans
`overlay_windows.rs` for the call.

`divora_capture::native::window` has `foreground_window()`,
`try_foreground(hwnd)` (`SetForegroundWindow`, nothing injected) and
`can_take_foreground(hwnd)` (`IsWindow`, `IsWindowVisible` and not
`IsIconic`). Windows are passed as integers, so `src-tauri` needs neither
`unsafe` nor the `windows` crate.

- **Focus** (entering Arrange): remember the foreground window in
  `return_to`, unless it is the overlay or none; `try_foreground` the overlay;
  log whether it worked.
- **ReturnFocus** (every Arrange → Locked edge): if the overlay still has the
  foreground and the saved window can take it (`should_return_focus`), give it
  back. Settings' Lock and the tray's leave the keyboard where it is: Divora's
  main window, or the tray's hidden window, has it then.
- **Refused.** Windows may refuse the overlay the foreground. Nothing else
  happens then. The chrome's hint follows the overlay's own focus
  (`document.hasFocus()` and focus/blur): "Esc locks the overlay" while it has
  the keyboard, "Click Lock to lock the overlay" otherwise. A click on the
  overlay focuses it.

**The hotkey acts in Rust.** `global_shortcut_handler` (`lib.rs`) calls
`overlay_windows::hotkey` before it emits `global-shortcut`. A press of
`overlay:arrange` is a toggle (`hotkey_overlay_request`); releases, which come
from global-hotkey's polling thread, and other ids do nothing. The mode changes
inline, on the main thread inside `WM_HOTKEY`, so the overlay asks for the
foreground while the press is fresh; a JavaScript round trip would ask later,
when Windows is less likely to allow it. It also works while main's
JavaScript is busy. The JavaScript branch (`noteOverlayHotkey`) never calls
`set_overlay_mode`, which would toggle the press twice. It only toasts "The
overlay is off. Turn it on in Settings first." or "The overlay is still
starting. Try again in a moment." While the overlay is closed, the hotkey does
nothing else.

### State

- **Main → overlay:** `overlay:state` (`OverlayState`, still 8 keys), a
  broadcast `emit` from `syncOverlay` (`src/overlay/sync.ts`) whenever the
  chain, the status, the tweaks or the background mode change while the
  overlay is open. The overlay animates on its own between pushes.
- **Overlay → main:** `overlay:ready` (no payload), emitted once the
  overlay's listeners are registered. Main answers with the current state and
  scene. The backend doesn't listen to it: it learns ready from
  `overlay_handshake`.
- **Backend → both windows:** `overlay:status` (`OverlayStatus`): `open`,
  `phase` (`closed` / `starting` / `shown` / `painted` / `closing`; a window
  being built reads as `starting`), `instance`, `mode`, `arrangeGen`,
  `canArrange`, `fit`, `hideWanted`, `hideAvailable`, `capturing` and
  `error`. No key says whether protection is applied: Windows doesn't confirm
  it. The overlay ignores a status for another instance.
- **Main → overlay:** `overlay:scene` (`ScenePush {session, revision, scene,
  ack, expectViewport}`), from `syncOverlayScene`: on every scene change while
  the overlay is open, and on each `overlay:ready` with `ack: null` (a reloaded
  page numbers its edits from 0 again). It is not part of `overlay:state`:
  `syncOverlay` re-sends the whole state on every status flip, which would snap
  a dragged picture back.
- **Overlay → main:** `overlay:edit` (`SceneEdit {instance, seq, op}`), one
  per finished gesture.

Each tauri `emit` is its own async command, so two sent back to back can
arrive in either order. Main's scene pushes and the overlay's edits each go
through one promise chain: an emit starts only once the one before it has
gone. Since v1.56.0 `syncOverlay`'s `overlay:state` pushes do too, because the
status can say Muted to an audience that relies on it; and none goes out
until main knows the mute or 500 ms have passed (see "Mute (v1.56.0)").

The ready signal is sent right after the listeners are registered, not after a
paint: the window is still hidden then, and stays hidden until the backend
hears the handshake, and a hidden page may not run animation frames. Painted
is its own signal, after the show.

**The overlay draws nothing until it has the state (for the circle) and a
scene (for the pictures).** The window can be shown before they arrive, and a
first frame of defaults would be captured by OBS.

The event names, the `OverlayStatus` and `ImportedAsset` keys, and sample
statuses are held once in `src/overlay/wire.fixture.json`. Rust
(`wire_fixture_matches_rust`, `imported_asset_wire_keys_are_frozen`) and
TypeScript (`status.test.ts`, `state.test.ts`) both read it, so a change on
one side fails the other's tests.

### The scene

`divora.overlayScene`, `{version, designSize, frame, elements[]}`, is the
first versioned localStorage key. Only main reads, migrates, writes and pushes
it.

- **Units.** An element stores `x, y, w, h` as fractions of `designSize`, in
  CSS px of the overlay's client area. A picture also stores `src` (an asset
  id, never a path or URL), `nw`/`nh` (its own pixels, as displayed), `anim`,
  `bytes` and `name`.
- **Layout** (`layoutElement`, pure). In viewport `V`, an element keeps its
  designed size in CSS px and shrinks, keeping its shape, only when it is
  larger than `V`. Its centre stays at the same fraction of `V`, clamped so it
  stays inside. The circle is laid out as the largest square in its rectangle,
  and Stage scales the circle's 440 px box (`SPELL_CIRCLE_PX`) by
  `min(w, h) / 440`. Elements stack by `z`, then by array order.
- **A `place` only grows `designSize`.** A `place` edit grows it to cover the
  viewport and stores the edited element as it is on screen. Every other
  element keeps its designed size and centre, and is left byte-for-byte
  unchanged when nothing grew. So shrinking the window and growing it back
  changes nothing.
  A drag or a nudge keeps a shrunk element's designed size and takes only its
  new centre; a resize takes the new size.
- **The shape is always kept:** `nw/nh` for a picture, square for the circle.
- **Frame.** `frame` says what `designSize` was measured against: the window,
  or the whole monitor (Fit to monitor). Changing Fit commits a `reframe` that
  keeps every element that lies wholly inside the new frame where it is on
  screen (one that doesn't is pulled inside it, shrunk if it is larger) and
  sets `designSize` to the new frame's size, so turning Fit off shrinks it to
  the window's.
- **Live and inert.** An element this version can show is live: the first
  usable `spellcircle`, and each `image` with usable geometry and an asset-id
  `src`. Anything else — an unknown type, a picture it can't recognise, a
  second circle, unusable geometry — is inert: kept exactly as stored, written
  back unchanged, neither drawn nor listed. Reading drops only entries that
  aren't objects or have no non-empty string id, and later duplicate ids. The
  caps (16 pictures, 64 stored elements, one live circle, and the budget
  under Charm pictures) apply when adding, never when reading.
- **Migration.** With no stored scene, `migrateScene` puts the circle where
  v1.51.3 drew it: at most 440 px, centred in the saved window (its size in
  `divora.overlay`, divided by its scale). That scene is saved the first time
  the overlay is seen open, before a geometry save can change what it was
  migrated from. A window under 440 CSS px now shrinks the circle; v1.51.3 cut
  it off.
- **The reducer** (`applyOp`: `add`, `remove`, `place`, `order`, `reframe`)
  is pure, rounds what it writes to 6 decimals, and returns the same object
  when nothing changes. Main and the overlay run the same function. The
  overlay may send only `remove`, `place` and `order` (`readOp`); main ignores
  anything else with a `console.warn`, and still acks it.
- The circle can be removed like a picture. Settings' Charms list then offers
  **Add the spell circle**, which adds it at the back.

**The mirror** (`mirror.ts`). The overlay draws the last scene main pushed
with its own unacknowledged edits applied on top, so a dropped picture stays
where it was dropped while its edit travels, and a push that crosses it
doesn't snap it back. An ack for its instance drops the edits it covers. A
new `session` (main reloaded) is adopted whatever its revision, and drops
every pending edit. Within a session a push is adopted only if its `revision`
is at least the one held. `expectViewport`, set only by a Fit change, keeps the
previous scene on screen until the window has that size, for at most 1 s
(`HOLD_MS`).

### Editing

Stage's rows are keyed by element id (the `ids`, `byId` and `rank` memos), so
a drag, an ack, a Settings change or a resize restyles a charm and never
remounts it: the circle keeps animating, a picture never reloads, and a
focused charm keeps focus. Rows stay in scene-array order and stack with
`z-index`, so restacking moves no node.

- **Pointer.** A press on a charm's hit layer (`[data-hit]`, at least 24×24
  CSS px, round for the circle) or on a corner handle (12×12, centred on the
  hit layer's corners) selects it and captures the pointer on its row.
  `pointermove`, `pointerup`, `pointercancel` and `lostpointercapture` are
  heard on `window`. A move only updates a preview; the `place` edit is sent
  once, on `pointerup`. A cancel or a lost capture drops the gesture and sends
  nothing, and a move with no button down ends it as a release. A corner
  resizes from the opposite corner, keeping the shape.
- **Keys.** The arrows nudge 1 px (Shift: 10 px). `=` and `-` (and the
  numpad's + and −) resize about the centre by 2 px on the long side; `+` and
  `_` by 10 %. A run of these is sent as one `place`, 300 ms after the last
  key (`NUDGE_FLUSH_MS`). Delete removes (Backspace doesn't); `[`, `]`, `{` and
  `}` restack. A pending nudge is sent before any other edit, a gesture, a
  lock or a change of selection, and when the window loses the keyboard.
- **Blocked.** In both modes every `keydown` is `preventDefault`ed except Tab,
  Alt+F4, and Enter or Space on a button (`shouldPreventKey`). That is meant
  to keep F5, Ctrl+R, Ctrl+P, Ctrl+F, F12, Ctrl+zoom, Alt+arrows and Alt+Space
  from WebView2: a reload would run the handshake again. The page has no
  `title` attribute (no tooltip), no `<select>` and no context menu
  (`contextmenu` is prevented), because WebView2's popups escape capture
  exclusion (WebView2Feedback #4544).
  The circle is `SpellCircle` with `decorative`: its nodes have no `title` and
  take no pointer or focus.
- **Entering Arrange** gives the stage the keyboard. `arrange` is a memo of
  the mode, so a status that keeps the mode (a take starting mid-arrange)
  doesn't move it. **Locking** sends a pending nudge, ends any drag and clears
  the selection.
- **The chrome** (Arrange only): a dashed frame; the **Lock** button top
  right, the toolbar's first control, an icon alone below 160 px wide; the
  **Move window** grip top left, not while fitted, its text from 320 px wide;
  and the hints, from 320×120: "Esc locks the overlay" or "Click Lock to lock
  the overlay", and "Recordings can see the overlay while you arrange." while
  a capture runs with Hide on and available (`capturing`, `hideWanted` and
  `hideAvailable`). A picture that won't load shows "Picture missing" while
  arranging. Locked shows no frame, outline or handle.

### Charm pictures

**Import** (`import_overlay_asset {path}`, on a blocking thread). The source
may be any regular file the user can read. It is refused when it:

- isn't a file, or is empty;
- is over 50 MB (counted in 10⁶ bytes, as Replay counts MB);
- isn't PNG, JPEG, GIF or WebP by its first bytes (an APNG is a PNG);
- is a JPEG that isn't baseline or progressive 8-bit (SOF0, SOF1 or SOF2 at
  precision 8): Chromium's libjpeg-turbo build has no arithmetic decoder, and
  Blink uses only the 8-bit API;
- has a zero side, or is over 8192 px a side or 16,777,216 px;
- is animated and over 4,194,304 px.

The size is as displayed: a GIF's logical screen grown to hold its first frame
(Wuffs' default, which Chromium uses), and a JPEG's width and height swapped
for EXIF orientations 5 to 8. Every header read is bounds-checked, so a
truncated file never panics. Only the headers are read: a file cut off before
its size is refused, and one cut off after it is still added. A PNG cut before
its first `IDAT`, or a GIF before its trailer, counts as animated, so the
animated cap applies.

The file is copied to `overlay/assets/<id>`. The id is the first 16 hex digits
of its SHA-256, a dot, and the sniffed type's extension (`png`, `jpg`, `gif` or
`webp`): nothing comes from the path. It is written as
`overlay/.import-<pid>-<nanos>.part`, beside the folder, synced (`sync_all`)
and renamed. The same picture added twice gets the same id and is written
once; a damaged or truncated file under that id is replaced. The answer is
`{id, width, height, bytes, animated, warning}`. `warning` is "Picture added.
It's a large picture, so the overlay may use more memory and CPU." over 20 MB,
or for an animated picture over 2,097,152 px, else null. The file picker offers
`.png`, `.jpg`, `.jpeg`, `.jfif`, `.jpe`, `.gif`, `.webp` and `.apng`; the
content decides, so the `.jfif` JPEGs browsers save are accepted.

**Budgets** (`addRefusal`, main, when adding only): 16 live pictures, 64 stored
elements, and, over the distinct pictures (a shared file counts once),
200,000,000 bytes of files, 16,777,216 animated pixels and 67,108,864 pixels
in all.

**The `charm` scheme.** `register_asynchronous_uri_scheme_protocol("charm",
…)`, so the overlay loads `http://charm.localhost/<id>` (`charmUrl`). The
handler runs on WebView2's UI thread and only hands the request to a blocking
thread. That thread takes one of two `ServeGate` places before it reads and
holds it until the response is handed back, so at most two pictures are read
into memory at once. That doesn't cap how many are held: a response handed
back waits, outside the gate, for WebView2's UI thread to copy it into a
stream, so while that thread is busy more than two can be held. `serve`
answers:

| Condition | Answer |
|---|---|
| the app's state doesn't exist yet | 503 |
| any webview but `overlay` (Settings shows no thumbnails) | 403 |
| a method other than GET | 405, `Allow: GET` |
| a path that isn't an id; a missing file; a file over 50 MB; bytes that don't match the extension | 404 |
| a read error | 500 |
| the overlay stopped being live while the file was read (checked last) | 503 |
| otherwise | 200, the type from the extension, `Cache-Control: public, max-age=31536000, immutable`, `X-Content-Type-Options: nosniff` |

The overlay is live from just before its window is built until
`CloseRequested`, or until the watchdog destroys it. tauri's `protocol-asset`
is not used: the dialog plugin widens the asset scope at run time for every
path it picks, and tauri's asset handler reads whole files on WebView2's UI
thread. The scheme adds no crate, Cargo feature or `tauri.conf.json` change,
and no absolute path reaches the DOM or localStorage.

**Removing.** After each change main counts every string anywhere in the scene
that is an asset id (`assetRefs`; inert elements and unknown keys included).
Each id whose count fell to 0 is queued for `delete_overlay_asset {id}`. The
queue checks the count again before deleting, and imports run on the same
queue, so a picture added again meanwhile keeps its file. A delete that fails
is logged. Files left behind (a failed delete, cleared app storage) are
harmless.

**Two folders.** `pnpm tauri dev` has its own localStorage, and so its own
scene; it keeps its pictures in `overlay/assets-dev`, so one build can't delete
the other's. The choice is `tauri::is_dev()`, not `debug_assertions`: a
`tauri build --debug` build has debug assertions on, but it shares the
installed app's localStorage and scene, so it keeps its pictures in
`overlay/assets` too. Both folders are under
`%APPDATA%\com.divora.voicemod\`, with a temp-folder fallback; the folder is
created and logged at startup.

### Hiding from recordings

**Hide from recordings** in Settings (off by default; shown only when
`hideAvailable`) asks Windows to leave the overlay out of captures
(`set_content_protected(true)`, `WDA_EXCLUDEFROMCAPTURE`) while Divora
records. It is a request: Windows doesn't confirm it, so no wire key claims
it. Only decoding a recording shows whether it worked.

- **When.** `protected()` is true when the toggle is on (`hideWanted`), it is
  available, the overlay is effectively Locked (Locked, or Arrange before its
  first beat), something captures (`capturing`), and the overlay's phase is
  Shown, Painted or Closing (a closing window's request stands while it is on
  screen). `capturing` is `capture_active(phase, replay)` in `screen.rs`: a
  take in any phase, or Replay in any state but Off, held included.
- **From the Show on, only on change.** The shell sets the affinity only
  once the window's Show effect has begun (the first time on the still-hidden
  window, just before it shows), and only when the wanted value differs from
  what it last set (`affinity_call`). So `WDA_NONE` never reaches a window
  that was never protected, and nothing reaches the window before its Show
  (Chromium skips the call on any hidden window, because it can leave the
  window blank). The Show effect marks the window shown, applies the window
  state, protection included, then shows the window, with no message pump
  between.
- **Order.** Towards Locked: click-through, the layered attributes (rung 1
  only; `R1_RUNG` is 0), resizable, then the affinity last, on that apply's
  final styles. Towards Arrange: the affinity off first, while the window is
  still layered. The order is an unmeasured hedge, based on reports of a
  `WS_EX_TRANSPARENT|WS_EX_LAYERED` window being captured anyway (Electron
  #29085, #47856).
- **Before a capture starts.** `ScreenRecorder::start` and `arm_replay` call
  `before_capture` after releasing the recorder's lock, before `open_feed`. It
  sets `capturing`; when protection is now due, it runs the apply on the main
  thread and waits for it, at most 300 ms, logging a warning if it isn't
  confirmed. It returns a `CaptureCleared` token, and `open_feed` takes one,
  so deleting either call, or moving it after `open_feed`, no longer
  compiles. A take's end (`finish`) and every Replay change (`publish`) call
  `note_capture` under the recorder's lock; `capture_hooks_are_in_place` is a
  source scan for those two, which the compiler can't check.
- **Arranging mid-take.** Protection goes off at the first beat, before
  click-through does, and the chrome says "Recordings can see the overlay
  while you arrange."
- **Windows 10.** The toggle is offered from `UniversalApiContract` 10
  (Windows 10 2004, `MIN_CONTRACT`), the first release with
  `WDA_EXCLUDEFROMCAPTURE`. Electron #47834 reports a click-through protected
  window still captured on Windows 10 (19045) and on Windows 11 21H2 (22000)
  when the affinity is set after the show, which is the usual order here. If
  a check on Windows 10 shows the same, `MIN_CONTRACT` rises to 15 (Windows 11
  22H2). `DIVORA_PRETEND_NO_CAPTURE_EXCLUSION` makes the toggle unavailable.
- **Other apps.** While it is protected, apps that capture your screen or the
  overlay window, OBS and Discord included, may not show it either — with
  Replay on, for as long as Replay is on. It applies whatever monitor Divora
  records; hiding only when the overlay is on the recorded monitor is a
  follow-up.

### Fit to monitor

- **Transparent only.** `effectiveFit(flags, bg)`: Fit counts only with the
  Transparent background. A stored Fit with Green or Magenta (written by mixing
  builds) reads as off, and nothing is written at boot. Settings disables Fit
  on a colour background, and Green and Magenta while fitted. Choosing a colour
  while fitted turns Fit off first; if that fails, the colour isn't applied.
  The overlay's background is transparent whenever `status.fit`, whatever the
  stored colour, so a fitted topmost window can't paint the screen.
- **`planFrame`** (`frame.ts`, pure) plans every open and Fit change. The
  window gets its monitor's whole rectangle (`fitRect`, through the same
  `pickMonitor` as `placeOverlay`) when Fit counts and the monitors could be
  read; else `placeOverlay(saved)`; else nothing, and Windows places it.
  `fit: true` goes to the backend only with a fitted rectangle. When the
  scene's `frame` differs from the target's, the plan adds a `reframe` between
  the two rectangles in the monitor's CSS px (`canvasRects`). An element
  wholly inside the new rectangle stays where it is on screen; one that isn't
  is pulled inside it, shrunk if it is larger. A Fit change made while the
  overlay was closed is reconciled at the next open, and saved before
  `open_overlay`.
- **While open,** main pushes the reframed scene, unsaved, with
  `expectViewport`, waits for that push to go, then calls `place_overlay`. On
  success it saves the scene and the flag and swaps geometry tracking for the
  fit keeper, or back. On failure it re-pushes the old scene and toasts the
  backend's words. Fitted since a fresh install (no saved place), Fit off puts
  the window where the reframe stood it in: a 480-logical square at the
  monitor's top-left.
- **One placement queue** runs open, close, Fit changes, the colour path and
  the keeper's re-fits one at a time, so a second click plans from a settled
  window. Imports and deletes have a queue of their own.
- **The fit keeper** (`keepFit`): the overlay's scale-change, resize and move
  events, settled for 400 ms, plus a check every 5 s, since a resolution
  change sends no event the overlay hears. If the window no longer equals its
  monitor's rectangle, the keeper places it again. tao keeps an undecorated
  window's logical size on `WM_DPICHANGED`, so after a scale change a fitted
  window would spill onto the next monitor.
- **While fitted** the window is not resizable and has no drag and no grip,
  and geometry saves stop, so `divora.overlay` keeps the user's own place for
  Fit off.

### Geometry

Everything is in **physical pixels**, because Tauri reports monitors,
`outerPosition`, `innerSize`, `onMoved` and `onResized` in physical pixels,
while the size a window is built with is logical. Main computes the rectangle;
since v1.55.0 the backend applies it.

**Saving.** After a move or resize settles (400 ms), main reads the overlay's
`outerPosition` and `innerSize`. It also reads the monitor under the overlay's
centre (`monitorFromPoint`). `currentMonitor()` would not do: it answers for
the window calling it, which is main. All of this is stored in
`divora.overlay` as `{ bg, x, y, w, h, monitor?, scale? }`, plus `fit` and
`hideFromRecordings` (v1.55.0; false when missing). Keys the build doesn't
know are carried through. The minimised parking spot (−32000) is never saved.
The place isn't updated while fitted.

**Restoring.** `placeOverlay` (`src/overlay/geometry.ts`) picks the monitor,
since v1.55.0 through the exported `pickMonitor`, which `fitRect` shares:

1. the monitor saved by name;
2. else the monitor the old rectangle overlaps most;
3. else the primary;
4. else the first monitor.

It then scales the size by the ratio of scale factors, so the window keeps its
apparent size if that display's scaling changed. Finally it clamps the
rectangle fully onto the monitor, with a minimum of 120 px.

**Applying.** `place_window` (`overlay_windows.rs`, on a tokio worker) sets the
size, then the position, then reads both back, repeating until they match, at
most three times. Windows rescales a window (`WM_DPICHANGED`) when most of it
crosses onto a monitor with a different scale, and that can happen during the
resize as well as during the move. The target rectangle lies wholly on one
monitor, so a second pass has nothing left to rescale. `open_overlay` places
the window before `Built`, so it never appears at Windows' spot and then
jumps. `place_overlay` checks the phase before it touches anything: "The
overlay is still starting. Try again in a moment." while the window is being
built, "The overlay isn't open." while closing or closed. Open's build-to-
`Built` and `place_overlay`'s placement hold one async lock, so two placements
never interleave. A rectangle whose width or height is 0 or over 32768 is
ignored: `open_overlay` leaves the window where Windows puts it, and
`place_overlay` moves nothing and leaves `fit` as it was. A negative,
fractional or missing field fails the call first, with Tauri's "invalid args"
error. When Fit doesn't count and there is no saved place, or when no monitors
could be read, the rectangle is null and the window opens at 480×480 (logical)
where Windows puts it.

### Moving it

Only in Arrange, and only when not fitted: Locked is click-through, so no
press reaches the window. A plain left press (`isPlainLeftPress`: button 0,
`detail` 1) on the **Move window** grip (`[data-grip]`), or on empty stage
(`startsWindowDrag`, `src/overlay/drag.ts`), calls `startDragging()`. Charms,
handles and the chrome are not empty stage. The circle's hit layer is round,
so the empty corners of its square move the window. A press on a charm calls
`preventDefault()`, which also stops the compatibility `mousedown`, so it never
drags the window.

It doesn't use `data-tauri-drag-region`, because Tauri's drag script toggles
maximise on a double-click for any resizable window
(`internal_toggle_maximize` checks `is_resizable` only). That would blow a
transparent, always-on-top window up to the whole screen. A drag may leave
part of the window off screen; the next open clamps it.

### Permissions

`capabilities/overlay.json` (v1.55.0) applies to the overlay alone:
`core:event:allow-listen`, `core:event:allow-unlisten`,
`core:event:allow-emit`, `core:event:allow-emit-to` and
`core:window:allow-start-dragging`. `allow-emit` is for `overlay:ready`, a
broadcast, and `overlay:edit`. `capabilities/default.json` now applies to
`main` only, and drops `core:webview:allow-create-webview-window`,
`core:window:allow-set-position` and `core:window:allow-set-size`: their only
users were main's creation and placement of the overlay. Main's tracking and
fit keeper read the overlay and listen to it through `core:default`.

Capabilities don't restrict app commands. There is no app ACL manifest
(`build.rs` is the plain `tauri_build::build()`), and tauri checks app commands
only when one exists, so the overlay can invoke every `#[tauri::command]`. It
relies on three: `set_overlay_mode` (Esc and Lock), `overlay_handshake` and
`overlay_alive`. `overlay.json`'s description says they must be granted if an
app manifest is ever added. The overlay logs failed calls with `console.warn`
(a failing beat once per Arrange), so a refusal would show in its console.

### Threads and locks

All ten overlay commands are `async`: Tauri 2 runs a sync command on the main
thread, which both windows share, and building a window from a sync command
deadlocks.

| Caller | Thread | Locks | Window calls |
|---|---|---|---|
| `open_overlay`, `place_overlay` | tokio worker | the placement lock (`tauri::async_runtime::Mutex`) from build or placing to `Built` / `Placed`; `core` briefly | build, setters and getters (`hwnd`, `outer_position`, `inner_size`, round trips to the main thread), never under `core` |
| `close_overlay`, `set_overlay_mode`, `set_overlay_hide_from_recordings`, `overlay_status`, `overlay_handshake`, `overlay_alive` | tokio worker | `core` | posted |
| the hotkey (`global_shortcut_handler`) | main, inside `WM_HOTKEY` | `core`, released before the window work | inline |
| the tray's Lock the overlay | main | `core`, released first | inline |
| `on_window_event` (`CloseRequested`, `Destroyed`) | main | `core`, released first | `RemovePropW` inline |
| watchdog, lease | `divora-overlay-watchdog`, `divora-overlay-lease` | `core` | posted |
| `capture_changed` (`note_capture`) | whichever thread ended a take or changed Replay, **under the recorder's lock** | `core` | posted, or inline on main after `core` is released |
| `before_capture` | the thread starting a take or arming Replay, **after** the recorder's lock is released | `core` | posts and waits ≤ 300 ms; inline on main |
| the `charm` scheme | WebView2's UI thread, then a blocking thread | a `ServeGate` place | none |
| import, delete | tokio blocking | none | none |

`step` takes `core`, steps, and emits the status while still holding it. Off
the main thread it posts the window work as one closure, still holding `core`
(posting doesn't wait, and keeps the order across threads). On the main thread
it releases `core` first and runs the work inline: an inline setter can send a
window event straight back into `on_window_event`, which takes `core`.

**Lock order:** the recorder's lock → `core`; the hotkey plugin's own lock, if
it holds one around the handler → `core`. `core` is a leaf: under it, code
only computes, emits and, off the main thread, posts the window work and
starts the watchdog and lease threads. The overlay never calls into the
recorder. There are no Rust event listeners, so tauri's listener lock is
not in the order.

**Main-thread hazards** (each a review item):

1. `WebviewWindowBuilder::build` only in async commands: from a sync command
   or an event handler it deadlocks.
2. Never hold `core` across a window call.
3. Never block the main thread on a channel: `before_capture` runs inline
   there.
4. Getters (`hwnd`, `outer_position`, `inner_size`) only on worker threads,
   never under `core` or the recorder's lock. `open` and `place_overlay` call
   them under the placement lock, which the main thread never takes.
   Main-thread code reads the stored HWND.
5. The tray menu is rebuilt only on the main thread.
6. The scheme handler never reads a file on the UI thread.
7. Never `set_focus` the overlay (a test scans for it).
8. Never register or unregister a shortcut from the hotkey path.
9. The reconcile setters never reach a window that isn't live
   (`reconcile_plan` is `None` in Closed, Creating and Closing), and the
   affinity reaches a window only from its Show effect on (the first time
   just before it shows). Outside that, `open`'s build sets click-through on
   the window it is creating, reads its HWND and places it, and
   `close_overlay` and the watchdog close or destroy the window as the core
   steps to Closing.
10. `before_capture` only after the recorder's lock is released; the token
    can't check that.

## Screen recording (v1.52.0)

One monitor to an MP4 — H.264 High plus AAC-LC 48 kHz stereo 192 kbps — with
the modulated voice and the soundboard, and since v1.53.0 what the PC plays
(on for a fresh install where Everything except Divora is offered; otherwise, and
after an upgrade, off until a source is picked on the card). The plan, the encoder ladder and what
comes next are in [`research/stream-studio.md`](research/stream-studio.md).

### Crates

- **`divora-capture`** (new) does the capturing and encoding and knows nothing
  of the engine, tauri or cpal. Its pure parts are tested on any machine:
  `pacer` (`FramePacer`), `sizing`, `nv12` (the CPU colour converter),
  `clock_fit` (`ClockFit`) and `timeline` (`AudioTimeline`). Everything that
  touches COM is under `native/`, the crate's only `unsafe` scope, and off
  Windows `elsewhere.rs` reports "unavailable" through the same API.
- **`divora-core`** gains the tap (`audio/av_tap.rs`) and nothing else that
  knows about recording — and, in v1.53.0, `AudioEngine::stream_info`, the
  live session's devices, for the desktop-audio guard.
- **`src-tauri`** gains `screen.rs`: `ScreenRecorder` in `AppState`, the
  commands, the `screen-recording` event, and `EngineFeed`, which turns the
  tap's chunks into the capture crate's.

### Media Foundation is loaded at run time

`native/mf.rs` loads `mfplat.dll` and `mfreadwrite.dll` with
`LoadLibraryExW(… SYSTEM32)` and resolves every free function it uses with
`GetProcAddress`. The `windows` crate would import them at load time, and on a
Windows N edition without the Media Feature Pack the app would then not start
at all. COM methods are vtable calls and import nothing.
`src-tauri/tests/no_static_media_foundation.rs` reads the built
`divora-app.exe`'s import tables, normal and delay-load, and fails on any
`mf*.dll` — verified by adding one static call, which it caught.

### The picture

```
WGC (CreateForMonitor, free-threaded pool of 2 BGRA buffers)
  └─ FrameArrived only signals the recording thread
divora-encoder thread (MTA COM, one per take)
  ├─ drain: newest frame → `latest` (BGRA texture), pool buffer returned at once
  ├─ FramePacer: constant-rate PTS (index·10⁷/fps); repeats on a still screen,
  │   counts ticks it fell behind on
  ├─ BGRA → NV12: the D3D11 video processor (BT.709, studio range, scaled to fit
  │   2560×1440, letterboxed if the screen changes shape mid-take) — or, where
  │   the device has no video support, a staging readback and
  │   `nv12::bgra_to_nv12` on the CPU (which stretches a changed shape)
  └─ sink writer (MPEG-4 by attribute, written as `.part`):
      H.264 via the DXGI device manager → hardware encoder where there is one;
      the encoder actually loaded is read back (`GetServiceForStream`)
```

### The sound

The output callback taps two signals where the soundboard is still separate
from the voice — after the chain, loudness and the mute (v1.56.0: a muted
voice goes in as zeros, never skipped), before the fold and before the
monitor-only previews — into preallocated rings, plus one mark per buffer:
cpal's callback instant, the buffer's index, the device frames it wrote, the
input ring's depth before the pop, and the chain's latency. Idle, each
callback does one atomic load. While recording, the output callback reads the
input ring's depth and makes three ring pushes a buffer, and the input
callback takes one timestamp difference and stores the input latency; one
`Instant::now()` per run — on the first buffer of a take, and again after an
engine restart — anchors cpal's instants to the clock the video uses. A buffer that doesn't fit in all three rings is
dropped from all three and counted, so marks and frames can never pair up
wrong. `av_tap.rs`'s tests measure the tap allocation-free (with a live-probe
control) and check that what goes in comes out.

The per-session `divora-av-tap` thread forwards every 5 ms over a bounded
channel. The recorder's sender lives on the engine thread, outside any
session, so a device-loss rebuild — or the user stopping and starting the
engine — hands it to the new session: the take carries on, silent while there
is no engine, and the event's `audioLostAt` says when that began.

`AudioTimeline`, on the recording thread:

1. **Steps.** A buffer well off `ClockFit`'s line (after cancelling scheduling
   jitter with the device frames it wrote) is a stall the call heard too; it is
   kept as silence, not averaged into the clock.
2. **Drops.** A jump in the index is silence of exactly that length.
3. **Placement.** The soundboard at its buffer's time. The voice earlier, by
   input latency + the input ring's depth (smoothed; moved only in a pause, or
   mid-word past 20 ms) + the chain's latency (exact; moves with the chain) —
   so Voice Convert's hold (18.4 ms with the bundled voice, 261.4 ms with a
   non-streaming model) doesn't put the voice behind the picture. Through
   v1.56.0 the chain reported 13 ms for the bundled voice while holding it about
   272 ms, so by the code the voice was placed about a quarter-second late.
4. **Clock.** `ClockFit` fits engine frames against the video's clock (drift
   held to ±0.5 %), and a Kaiser-windowed sinc reads the mix at the fitted
   positions straight into 48 kHz, so the track neither slides over a long take
   nor depends on the engine's rate.

A sample with no audio is written as silence once it is a second old, so the
track never stalls the file; at the end the timeline waits up to 1.5 s for the
audio to catch up to the last frame.

### Desktop audio (v1.53.0)

What the PC plays, mixed into the same AAC track. Two sources, one loop:

- **Everything except Divora** — *process loopback*
  (`ActivateAudioInterfaceAsync`, `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`
  on Divora's own PID): every other process's audio, on whichever device it
  plays, without Divora's voice, soundboard or monitor — or anything Divora
  started — except on a device loopback can't hear: on the development PC,
  the default Realtek USB speakers (which have a vendor virtual mixer) were
  silent to both loopbacks. Whenever another app opens or closes a stream on
  a device, Windows skips about 15 ms of that device's sound and then sends
  30 ms of zeros (measured with a tone playing throughout on the same device;
  endpoint loopback had the tone whole; other devices untested), which the
  timeline counts as a gap.
  Offered only after a trial activation works (and Windows 10 2004,
  `UniversalApiContract` 10, or later).
- **One playback device** — *endpoint loopback*, `device:<id>`: everything
  that device plays, Divora included. Offered where process loopback isn't.

Both are hand-written in `divora-capture` (`native/loopback.rs`) on the same
`windows` 0.61 the crate already uses, and ask Windows for the same thing:
48 kHz float stereo, converted from whatever the device runs at.
`ActivateAudioInterfaceAsync` is resolved at run time like Media Foundation,
so the exe gains no mmdevapi.dll import; its parameters live in a heap blob
owned by the `#[implement]` completion handler — never dropped as a
`PROPVARIANT`, whose `Drop` in windows 0.61 would hand them to
`CoTaskMemFree`.

```
divora-loopback thread (MTA COM; while a stream is open, registered with the
  │  multimedia scheduler's "Audio" task — avrt.dll resolved at run time — or at
  │  HIGHEST priority where that fails)
  desktop_thread::run — open, report, pump, reopen on loss (backoff 1 s → 30 s;
  │  a hung activation is not retried, and says so: the card then shows a
  │  final error, not "trying again"); generic over PacketSource/Opener so
  │  CI drives it with scripted devices; a playback device's first packet
  │  after a quiet wait is marked as a resume (silence before it, not loss)
  ├─ wait ≤ 20 ms on the stream's event; every wake: GetNextPacketSize
  │   (where a dead stream reports), ≤ 64 packets; a playback device that
  │   timed out is asked GetCurrentPadding (an idle device sends nothing);
  │   process loopback that sends no packet for 1 s is treated as lost (on
  │   Windows 11 26200 it sends one every 10 ms, even in silence)
  └─ per packet: packet_time (the packet's QPC on the Instant clock, from one
      anchor pair; arrival − length if flagged or > 1 s off) → DesktopTap::ingest
      (preallocated rings, all or nothing, no allocation — tested) → ReleaseBuffer
recording thread: AudioTrack (track.rs) polls the engine and the desktop,
  pushes both before asking the timeline what is ready
```

In `AudioTimeline` each source has its own lanes (`Lane<C>`, the resampling
half of v1.52.0's epoch, made generic over channels): the engine's epochs as
before, and desktop **runs**. A packet continues the open run only if it
lands within 7.5 ms of the run's line (40 ms for one Windows could not time);
anything else — a lost packet, an idle device coming back, a flagged break, a
reopened device — starts a run on a line of its own, never a step bridged
across the gap. A run's first three packets set where it sits rather than
vote on it, and no resampler starts on a run until they have — or the
recorder, pumping between packets, would glide after a moving line. Every
run that reaches an output frame is summed, so where one
ends and the next begins with nothing lost there is no seam. A frame is
written once each source has delivered it or is overdue (the engine after
1 s, the desktop after 0.25 s — an idle device sends nothing), and only then
is the silence counted.

With desktop audio the track is stereo: the voice and soundboard in the
middle, the desktop at its volume around it, through a soft knee above
−3 dBFS. Without it, the track is v1.52.0's to the bit — pinned by
fingerprints taken from v1.52.0's own code.

Opt-in **stems** (`stems.rs`): `.voice.wav`, and `.desktop.wav` when the take
has desktop audio, 48 kHz float, the very frames the track is mixed from. The
MP4 has no edit list. Over five takes (three short, two of 30 minutes), 79 of
80 soundboard stings were measured at the same sample in its decoded audio as
in the voice stem, and the other one sample apart (in the 30-minute take
before the code review's fixes); on each take the stems were the same length
as the decoded audio, to the sample. Past a WAV file's size limit (about 3.1
hours with desktop audio, 6.2 without) they stop, `stemsError` says where, and
the video goes on.

The **doubling guard** for playback devices (`screen.rs`): what Divora plays
on each device — `send`, `monitor`, `onlyOutput`, `nothing`, `unknown` — from
the engine's routing (`AudioEngine::stream_info`, kept by the engine thread),
matched by device name, the engine's own notion of identity. A device Divora
sends your voice to when a take starts is not recorded. During the take the
desktop feed (`EngineFeed`) reads the engine's routing each time it takes in
desktop audio — every pump, about every 20 ms — and while the recorded device
is one Divora sends your voice to, what it takes in goes in as silence;
`desktopError` says why, updated with the card once a second. The engine
publishes its routing just after its streams start, before a voice could come
back through loopback, so none of it should get in. Measured: with Divora's
output moved onto the recorded device mid-take and back, the device's clicks
(one a second) were left out between the switches and kept before and after,
and Divora's stings there were exactly 0; the switch times are known only to
the second, and that nothing slips through in the first milliseconds is
reasoned, not measured. On the
others the card warns before the take, and `desktopDoubled` reports when the
running engine's monitor switches put Divora's sound there during it.

## Replay (v1.54.0)

The last 15, 30, 60 or 120 seconds of one screen — the picture, the voice and
soundboard as the call hears them, and the desktop audio the card records —
kept in memory and saved as an MP4 on request: from the card, a hotkey or the
tray. Off at every launch: nothing saved turns it on. The first time, only
"Turn Replay on" in the card's explainer turns it on, and the explainer is
needed again if desktop audio is on now but was off when it was read; after
that, the card's switch or the `replay:toggle` hotkey does. Divora writes no
picture or sound to disk until Save. That promise is about Divora: Windows may
still page the ring to its page file, or write it to `hiberfil.sys` when the
PC hibernates. The design, with its review, is in
[`research/stream-studio.md`](research/stream-studio.md) ("As built").

### One pipeline, shared

A take and the ring share **one capture pipeline**: one WGC capture, one
hardware H.264 encoder driven directly, and one audio timeline, on one
`divora-encoder` thread (`divora_capture::spawn_pipeline`). A take started
while Replay is on goes on Replay's pipeline (with Replay's settings, or it is
refused); an arm during a take joins the take's pipeline (on its settings). The
pipeline ends when neither needs it.

```
src-tauri ScreenRecorder (AppState.screen) — Shared, one lock:
  phase/take… (v1.52.0) · slot: Slot<PipelineHandle> (None | Running | Ending)
  · settings: SharedSettings · desktop: DesktopReport · replay: state, seconds,
  saving, last save
    │ PipelineCommand (mpsc + Wake)          ▲ PipelineEvents / TakeEvents
divora-encoder thread (MTA) — Runner (native/pipeline.rs) around PipelineCore:
  ComScope, MfSession (dropped last) · Session { encoder, pool, converter,
  latest, capture, mf_device, gpu } (dropped in that order)
  PipelineCore (pipeline_core.rs, pure): FramePacer · OutputRouter
  (SubmitQueue + KeyframeWatchdog) · EncoderLiveness · AudioTimeline (stems
  on, 600 s fit window) · BlockTail (600 ms) · TakeCore · ReplayRing +
  PendingCut
    ├─ divora-take-mux (one per take): Mp4Writer + StemWriter → rename
    └─ divora-replay-save (one per save): Snapshot → Mp4Writer → rename
```

**The encoder thread writes no recording or clip** (its log lines are its only
file writes): it hands a take's messages and each save to threads of their own
without waiting. Once running, a turn of its loop waits at most 20 ms (2 ms
while a frame waits for the encoder). Its longer stalls:

- the first picture at the start (up to 5 s, before it reports ready);
- a drain (up to 500 ms) when the encoder's last output is wanted — a take
  ending, the screen gone — or a quiesce (up to 100 ms) when it isn't;
- building again: a new encoder and pool after a stream change, new capture
  buffers when the screen changes size, a whole session after a sleep (each
  try a stall of its own; the loop turns between them);
- at the very end, the desktop-audio thread's stop (up to 2 s).

It logs transitions and failures only — every log line is a synchronous file
write. Its encoder's counters go in one line when a session is let go or the
pipeline ends, not when a sleep drops the session or a stream change replaces
the encoder. In a 26-minute armed run (on the build before the review's fixes)
it wrote no line after it began keeping the screen; the only later line in the
log was the save thread's, for the save at minute 5.

**`PipelineCore` makes the pipeline's decisions** about takes, the ring, saves
and faults, and is driven in CI by a pretend encoder, engine and shell. The
Windows shell keeps the timing and a few checks of its own: after a sleep it
tries the rebuild every 2 s for 30 s and makes a new capture after 10 s with no
picture; it asks the graphics device once a second whether it is still there;
it ends a take whose writer can't keep up; and it replaces a frame still
waiting for the encoder with the newer picture. The core's calls that act fill
an `Out` the shell passes in: messages for the open take's writer, clips to
save, what to do with the session — `Drain` (a take ends with nothing else
needing the screen: the border goes, the encoder hands back what it holds),
`Release`, `RebuildEncoder` (the encoder restarted itself), `Rebuild` (after a
sleep) — and whether the thread should end.

### The encoder, driven directly

`EncoderSession` (`native/mft.rs`) drives the hardware H.264 MFT itself
instead of the sink writer: async, D3D11-aware, fed NV12 textures from a pool
of four (`InputPool`, an `IMFVideoSampleAllocatorEx`). It must accept the
pipeline's bitrate (what a take with those settings uses), forced keyframes,
and a GOP of 2 s (set before the output type, read back, refused if the encoder
says otherwise). It asks for CBR, low latency and no B-frames; a refusal of
any of those is logged, in "the direct encoder is ready", and is not fatal.
NVIDIA accepts CBR and low latency and refuses the B-frame count, but makes no
B-frames; any B-frame is caught on the output (DTS ≠ PTS).

A keyframe is forced where a take or a ring segment starts, and whenever a GOP
of input (2 s) has gone by since the frame of the last IDR that came out
(`KeyframeWatchdog`; never while a forced one is still on its way). Outputs
are matched to the frames submitted (`SubmitQueue`) by their timestamps — a
later one means the encoder dropped a frame, none means it re-stamps. An
encoder that stops answering, or stops asking for input, for more than a
second is caught (`EncoderLiveness`).

**An encoder that can't be trusted is remembered until the next launch.**
Re-stamped outputs or B-frames end a take at its last frame and hold the ring.
A forced keyframe more than 3 frames late, or a ring segment that goes more
than two GOPs and 0.1 s without an IDR (`RingFault::NoKeyframe`), holds the
ring ("This PC's encoder doesn't make regular keyframes."); a take already
running carries on. That is said once; later late keyframes are only counted,
and the count is logged in "the pipeline ended" only if the session lasts
until then — not when a ring held for it lets the session go first. After any
of these, no take or arm uses the direct encoder until the next launch. A
stall, a lost device, a stream change or a failed rebuild is not remembered.

**Rung 1 stays.** A take goes through v1.53.0's sink writer on a PC without a
hardware encoder, on a run where the direct encoder failed to build or was
found untrustworthy, and — only for a take started while no pipeline runs —
with `DIVORA_CAPTURE_RUNG1` or `DIVORA_CAPTURE_CPU_CONVERT` set. A take whose
direct encoder fails to build goes on as the same take, with the audio feed it
already opened (`StartError::Direct` hands it back). Any failure of the parts
only the direct path uses — the encoder, its device and input pool, the GPU
colour converter — counts as "failed to build", even when its cause passes
(an encoder whose sessions another app holds): the take falls back, and
Replay is unavailable until the next launch. The capture and the GPU device,
which the sink writer shares, still refuse the take. With Replay on, a take
goes on Replay's pipeline whatever the switches say, or is refused. Replay needs the direct encoder: `replay_support` says why
it can't run — screen recording unsupported, no hardware encoder, or the
direct encoder failed on this run. The switches never stop Replay; they only
get an arm refused (`RUNG1_TAKE`) while a take they sent to the sink writer is
running. `DIVORA_PRETEND_NO_DIRECT` refuses the direct encoder to check that
path.

### Takes on the pipeline

A take starts at the next frame, `k0`, with a keyframe forced there; its file
opens on the first keyframe at or after `k0` (never an earlier one), with that
keyframe's in-band SPS/PPS, or the session's header if it carries none. Its
audio is cut from the shared timeline at
`sample_of(k0) = k0·48000/fps` — exact at 30 and 60 fps — seeded from the last
600 ms of blocks the timeline handed out (`BlockTail`), because with an A/V
offset the timeline runs ahead of the picture. A stop ends the take after the
last frame submitted and waits (≤ 1.5 s) for that frame and its audio; the
take's writer, on its own thread, finishes the file and tells the app —
exactly once, however the take ended. Its audio is sent only as far as its
video has gone, give or take the one 1024-frame block that straddles it, so a
take cut short (an encoder that stalls, a sleep) has less than a block (about
21 ms) of sound past its last frame. A writer 4096 messages or 64 MiB of
encoded video behind ends the take ("The disk couldn't keep up"), its file
kept. The take reports its own counts (frames, drops, the timeline's counters
since it began) and the pipeline's gauges as they are (drift, the voice's
delay).

### The ring

`ReplayRing` (`replay.rs`, pure) keeps access units and the timeline's mixed
track (a PCM ring of `seconds + 4` s, allocated when the ring is made and
again, keeping the newest audio, only when the length changes while Replay is
on):

- **Whole GOPs leave the front**, never single frames, so the front is always
  an IDR: by time while the next IDR is `N` seconds old, and by bytes over the
  cap; the audio under them goes with them. Once full, the ring holds `N` plus
  part of its front GOP: about `[N, N + 2 s)`, a little more when a forced
  keyframe comes late (the test allows `N + 2 s` + 5 frames; the 26-minute run
  at 30 s, on the build before the review's fixes, held 30.1 to 31.95 s).
- **One segment at a time**, one header and one unbroken clock: a header
  change, the engine coming back after a hold, a rebuilt encoder or a sleep
  starts a new one, which clears the ring. A segment's audio is clipped to its
  first frame's sample and seeded from the block tail.
- **Save** cuts the window from the latest IDR at least `N` before the frame
  showing at the press (or the front, if the ring is shorter), pins its first
  GOP against eviction, and waits — never blocking the loop — until the ring
  has that frame and its audio, at most 1.2 s (missing audio is silence). The
  snapshot shares the access units and copies the audio. A save thread checks
  the drive's free space (under 1.1 × the snapshot's size, its video plus raw
  audio: refused, no file written), writes `.part` in time order (audio pieces
  of 100 ms interleaved with the frames, both streams from 0, no edit list;
  throttling off, paced on the writer's queue), renames it, and answers.
  Every Save is answered exactly once (`SaveReply` answers "wasn't saved" if
  dropped), so `replay-saved` goes out once per attempt.
- **Held**: the engine stopped by the user (or its recovery gave up, or it has
  been down 5 s), the screen gone, or the encoder failed: the ring keeps what
  it has, takes nothing new, and a Save still cuts from it; with the engine
  stopped, the timeline's last epoch is closed first, so the soundboard that
  played just before the stop is in the clip. A hold with nothing kept —
  before the first keyframe, or after a sleep emptied the ring (one held for
  the engine waits for it) — turns Replay off, and so does a rebuild that
  fails (the owner's decision: off, where the plan had it held).

**Memory**: `estimate = (N + 2) · bitrate/8 + (N + 4) · 192 kB`, the cap 25 %
over it (what the UI shows, "up to … MB", rounded up), refused past
`min(1 GiB, RAM/8)` (`ullTotalPhys`; shown rounded down). The default — 30 s at
1440p30 Balanced — is up to 81 MB.

### The engine watch and the tap

A device-loss rebuild leaves `is_running()` false for its length, so the ring
can't hold on that: `AudioEngine::user_stop_count()` (divora-core) counts the
user's stops — each Stop, and each Start whose devices won't open — and
`EngineWatch` holds the ring on a count that moved, a recovery that gave up, or
5 s of not running. A device switch in Settings restarts the engine without a
Stop (`restartEngine()`): one that comes back up is a rebuild the ring carries
on through (silence in the gap); one whose devices won't open has already torn
the running session down, counts as a stop, and holds the ring.

**The tap numbers its takes.** A take or an arm waiting for the last pipeline
to end attaches the engine's tap the moment that pipeline lets go of it. When
the output callback had not run in between, it never saw the tap disarmed: it
started no new run, the drain had already dropped the old one, and every
buffer of the new take was thrown away (found in the real app: a take started
right after another had no voice or soundboard). Each attach is now a numbered
take; the callback stamps each buffer with it and starts a run when the number
changes; the drain reads its control messages first, forwards only the
attached take's buffers, drops older ones and keeps newer ones for their
attach. In a debug build of the shipping code, a take started right after
another, and a ring armed right after Replay was turned off, each had 3 of 3
soundboard stings.

### Sleep

`Instant` counts sleep on Windows, so no reading of it from after a sleep may
reach the timeline. Each turn of the loop — the encoder thread's, and the sink
writer's — reads the clock once, then checks for a sleep (`SleepWatch`:
Windows' resume notification, plus the performance counter running ahead of
the interrupt time), and uses that one reading for all its work; only the
wait's length reads the clock live. On a sleep, the moment things end at is
the reading the previous check was given (`sleep::LoopSleep`): from before the
sleep, whether the PC went down in that turn's work or its wait.

Then the feed's contents are thrown away, a take ends at its last frame before
the sleep, its file kept (rung 1 too, through `AudioTrack::finish_at`), a
pending Save is cut there, and the ring's session is rebuilt: at once, again
every 2 s for 30 s, then waiting for a picture for as long as the lock screen
takes, on a new clock. Until that picture, a take is refused ("The screen
isn't sending a picture yet — try again in a moment."), and nothing on the
old clock reaches the timeline: what the feed brings meanwhile is thrown away,
and the first picture starts a new timeline on a new clock. A take's finishing
wait on the sink writer never pumps more than 2 s past its end, so a sleep
during that wait adds at most about a second of silence after the end, never
the sleep.
A ring held for a lost screen or a failed encoder has nothing to keep with
again, so a sleep that empties it turns Replay off; one held for the engine
stays held, empty, until the engine is back.

**None of this has been through a real sleep.** It is covered by tests only:
the pure core given the moment of a sleep, `LoopSleep`, and the bounded
finishing wait.

### The app

`replay.rs` (src-tauri) is the rules, all pure and table-tested:

- the `ReplayState` table: Off → Arming → Armed → Held. A rebuild sends an
  armed ring back to Arming, and so does the engine's return to a ring held
  for it; a ring held for a lost screen or encoder stays held until Replay
  turns off. Whatever would hold a ring still arming turns it off, as do a
  Disarm, Replay turning itself off (a failed rebuild, an emptied hold) and
  the pipeline's end;
- the `Slot` (None / Running / Ending), which tells a take's start or an arm
  to wait while the pipeline is on its way out — up to 3 s (`SLOT_WAIT`),
  then it is refused;
- `SharedSettings` and the refusals in the user's words, `EngineWatch`, the
  memory table, file names (`divora-replay-<date>_<time>.mp4`, from local time
  — the tray saves with no window), the tray view and Quit's wait;
- the wire shapes: `ReplayStatus` with its `ReplayArmed` and `HeldReasonDto`,
  `ReplaySaved`, and `ReplayMemory` with its `ReplayLength`; `ReplayState`
  goes out as its name.

`screen/replay_ops.rs` applies them. `screen.rs` also holds a take's start or
an arm for up to 8 s while a pipeline is still being started (`SPAWN_WAIT`),
then refuses it with "Still stopping the last recording — try again." The
`ended` event detaches the engine's tap before it frees the slot, so a new
pipeline's tap always comes after. A Stop or a Disarm pressed while the
pipeline is still being built is carried out the moment it is ready
(`spawned`), and events from a pipeline that ended before then are not
overwritten by it.

The tray (`lib.rs`) is synced through `run_on_main_thread` (`sync_tray`),
without waiting: the tray's setters block off the main thread, and Quit holds
that thread while it waits. The one exception is Quit's "saving replay…"
tooltip, which `quit_replay` sets directly, already on the main thread. While
Replay is on, the tooltip says so (and with desktop audio) and how the last
save went, the icon gains a red dot, and the menu gains Save replay and Turn
Replay off — never a way to turn Replay on.

From v1.55.0 the menu is built from `TrayItems {replay, lock_overlay}` through
`tray_entries`: Show · Save replay · Turn Replay off · Lock the overlay ·
Quit, each optional group set off by separators and shown only while it
applies. `sync_tray` keeps Replay's half in `TRAY_REPLAY`, so the overlay can
rebuild the menu without asking the recorder. `refresh_tray_menu` rebuilds
only the menu (not the tooltip or icon), also on the main thread, when the
overlay enters or leaves Arrange and when its window goes. The menu gains
Lock the overlay (`overlay-lock`) only while arranging; it never starts
Arrange.

Quit waits for a save in progress for as long as its size needs (5 to 60 s,
plus the cut's 1.2 s, worked out again once the clip is cut), then cancels it
and waits up to 10 s more. A save still writing stops within 16 writes, lets
go of its file unfinished and removes the `.part` (retrying for a second while
Windows still holds it). One already finishing its file can't be stopped: it
has the writer's queue to flush — kept to about 4 MiB, but checked only every
16 writes, so up to 16 more can be queued on top — and then the file's index
to write.

The frontend's `armReplay()` is the only caller of `arm_replay_buffer` and
holds the explainer gate, for the card, the `replay:toggle` hotkey and anything
added later: while the explainer is still needed (above), every way but its
"Turn Replay on" is refused with a toast. A length picked while Replay is held
is applied, through it, once the ring runs again. The save toast names the
preset only if the voice was disguised with it from at least 3 s before the
clip began, judged back from the save — or, for a held ring, from when it was
held, where its clip ends. The toast is one always-mounted live region; while
the window is hidden — and WebView2 still says `visible` for a window hidden
to the tray, so it asks the window too — the latest toast waits until the
window is shown.

## Mute (v1.56.0)

Mute silences your voice everywhere Divora sends it — the call, the headphone
monitor and Divora's own recordings (the WAV recorder, screen takes and their
voice stem, Replay) — while the soundboard, Speak and Critter Chatter keep
playing. Both edges fade over a few milliseconds, so neither is a hard cut.
Every way in drives one state the engine owns: the `mute` hotkey (acted on in
Rust; a key a Stream Deck **Hotkey** action can send), a MIDI pad or CC, a
glyph bound to Mute / unmute, and the Mute button on the Mixer's Voice status
card.
Until v1.56.0 the glyph's mute changed only the status label (`ui.muted`), and
the voice kept reaching the call. It mutes Divora's voice, not the microphone:
an app that reads the microphone itself still hears you. The plan, and what
changed from it, are in [`research/stream-studio.md`](research/stream-studio.md)
(v1.56.0, "As built").

### The state

`EngineState.input_mute` is one `AtomicU64` holding `seq << 1 | muted`
(`audio/mute.rs` packs and unpacks it). `seq` counts changes since launch:
every change bumps it by one, and of two states the larger `seq` is newer. A
set to the value it already has changes nothing, `seq` included.

`AudioEngine` changes it with atomic operations on that shared state, never
through the engine's command channel, so a mute lands on the next buffer from
any thread, while the engine is stopped, and while the engine thread is
blocked inside a Start (`a_mute_lands_while_the_engine_thread_is_busy`):

- `set_input_muted(bool)` and `toggle_input_muted()` run one compare-and-swap
  loop (`EngineState::apply_input_mute`: `fetch_update`'s loop written out,
  since that name is deprecated on current stable and `try_update` is newer
  than the workspace's `rust-version`) and return `MuteChange { before, after }`
  from it; `before == after` means the call changed nothing.
- `input_mute()` loads the word once and returns `InputMute { muted, seq }`.

The commands `set_input_muted {muted}`, `toggle_input_muted` and `input_mute`
are sync, each makes one of those calls, and each answers an `InputMute`: the
state after. They never fail, apart from Tauri's own error for a `muted` that
isn't a boolean.

**Lifetime.** The word lives in `EngineState`, one `Arc` for the engine's
life, and teardown never touches it. Stop, Start, a device switch and a
device-loss rebuild keep the user muted, and a mute made while stopped holds
for the next Start (`input_mute_survives_stop_start_and_a_rebuild`). It is
never stored: every launch starts unmuted, at `seq` 0.

### The gate

`MuteGate` is built once per session in `build_output_stream`, beside the
cushion, where the word stands:
`MuteGate::new(mute_ramp_len(input_rate), state.input_muted())`. So a session
started or rebuilt while muted sends no voice from its first buffer, and a
take or Replay running through the rebuild gets no blip. The gate is the
closure's state, on the audio thread; the word is the engine's.

It holds one position, `pos`, in `0..=2L`, on a two-segment linear path. Each
sample moves `pos` one step toward its target — 0 muted, `2L` unmuted — before
that sample is scaled. The chain's input gets `min(pos, L)/L`, and the voice
after loudness gets `max(pos − L, 0)/L`:

```
pos (L = 4 shown)          0   1   2   3   4   5   6   7   8
the chain's input (feed)   0   ¼   ½   ¾   1   1   1   1   1
the voice (mute)           0   0   0   0   0   ¼   ½   ¾   1
```

- **Mute** fades the voice out over L samples, then the chain's input over L
  more. **Unmute** opens the chain's input first, then the voice.
- A toggle mid-fade turns round from where it is. Both gains are continuous in
  `pos`, so turning round never steps.
- The voice's gain is the outer one, so it reaches exactly zero L samples after
  the callback first sees the mute, whatever the chain still holds. At unmute
  a tail the chain still holds fades in rather than stepping in, and since the
  chain's input fades in too, an echo can't bring the unmute back as a step
  (`the_chain_input_fades_in_at_unmute`).
- With a passthrough chain the send is an exact linear ramp, with no step
  larger than the fade's slope (`no_step_larger_than_the_slope`,
  `the_send_is_a_pure_linear_ramp`).

**L** is `mute_ramp_len(rate)` at the engine (input) rate: the power of two at
or above 5 ms (`rate.div_ceil(200)`), clamped to 64..=2048. That is 256 at
44.1 and 48 kHz (5.8 and 5.3 ms), 512 at 88.2 and 96 kHz, 1024 at 176.4 and
192 kHz and 128 at 16 to 24 kHz; between 5 and 10 ms for every rate from 12.8
to 409.6 kHz, and 64 below that (8 ms at 8 kHz). A power of two makes every
gain `k/L` exact in `f32`, so both ends of a fade land exactly and the tests
compare without an epsilon.

`gate.run(muted, frames)` plans one buffer — where `pos` starts and where it
ends — and both passes, `feed` and `mute`, walk that plan, so neither their
order nor the buffer sizes change what they compute
(`feed_and_mute_share_one_plan`, `buffers_of_any_size_give_one_result`).

### Where it sits

Inside `mix_voice_and_soundboard`, the voice stage the callback already had:

```
output callback, per buffer:
  denormals::flush_to_zero()                 FTZ | DAZ (below)
  drains → chain latency → resample_pop → loudness params
  reading DRY tap                            the raw mic
  let muted = state_for_callback.input_muted();   one Acquire load
  mix_voice_and_soundboard(…, &mut mute_gate, muted, input_rate):
      run.feed(mono) → modulator → chain → loudness → run.mute(mono)
      soundboard.mix_into(sb)                untouched
  reading WET tap                            zeros while muted
  AV tap (takes, Replay)                     voice zeros, sb intact
  monitor ring                               the mic copy (zeros), sb, previews
  no monitor device: previews into mono      still audible
  fold: mono += sb                           the send = the clips (+ previews)
  WAV tap → resample_render → fan-out → OUT meter
```

"After loudness, before the soundboard fold", as the plan put it, is not one
point: between the two sit the reading's WET tap, the AV tap, the monitor's
mic copy and, with no monitor device, the previews mixed into `mono`. Muting
before all of them makes every recording match the send and leaves the
soundboard and the previews alone. A chain swap replaces the chain only; the
gate sits outside it, beside loudness. No test can run the callback's closure
without a device, so `the_output_callback_mutes_the_voice_stage` reads the
source, as the soundboard drain's test does: the gate built once, outside the
closure, at the word; the word read once and passed to the stage; the order of
the stage, the taps and the monitor; and the flush as the closure's first
statement.

### Starving the chain

`feed` closes the chain's input too, so while muted the chain hears only
silence. Zeroing the voice after the chain alone would keep the chain running
on the live microphone, and at unmute it would let out what it still held of
words said while muted: about 18 ms through Voice Convert with the bundled
voice (a quarter-second through v1.56.0), seconds through an Echo with high
feedback. Starved, what is said
once you're muted never enters the chain
(`what_is_said_while_muted_never_reaches_the_send`). What is said right around
the press can still enter: up to a buffer before the callback reads the word,
then 2L samples while the voice and then the input close — about 10 to 21 ms
at 48 kHz with 480-frame buffers. `STARVE_CHAIN` in `mute.rs` is the kill
switch; `false` makes `feed` a no-op.

**What the press cuts.** The voice closes first, so what the chain still holds
at the press — speech from just before it — is cut with it: the delays of the
chain's effects added up, 10 ms for a denoiser and 21 ms for each pitch or
formant effect, so 43 ms or more in the 10 of the 24 bundled presets that run
both pitch and formant; nothing with a passthrough chain. A voice model loaded
in Voice Convert adds its hold (Phase 12, "The hold"): 18.4 ms with the bundled
streaming voice, plus about 5 ms inside the model, or 261.4 ms with a
non-streaming one, so Deep Narrator with the bundled model cuts about 75 ms.
Through v1.56.0 it added about a quarter-second whatever the model — the
downsampler's whole 4096-sample rounds — and Deep Narrator cut about 0.31 s.
Both are worked out from the code and the tests' probes, not measured in the
app: no voice model was loaded in the real-app run. Keeping those words would
mean holding the send open for the chain's delay, which
`EffectChain::latency_samples` now reports (bar the model's own few
milliseconds). After an unmute the voice enters a
chain that held silence, as after any pause, and the reactive envelope
(`modEnv`) falls to rest while muted.

### Exact zero

Where a gain is 0 the stage writes `+0.0` (`fill`, or an assignment), never
`x · 0`, which keeps a NaN — and loudness passes a NaN through while it is
off. So once the fade is over the voice is `+0.0` whatever reaches it
(`nan_is_zero_once_silent`), and the fold's `0.0 + s` leaves the send equal to
the soundboard exactly. `feed` writes exact zeros too, from 2L samples after
the callback first sees the mute until the unmute. Where both gains are 1 the
gate leaves the buffer untouched; `an_open_gate_is_bit_exact` checks that with
a signalling NaN, which an x86 multiply by 1.0 would quiet.

### FTZ and DAZ on the output callback

A long mute — minutes, on a break — feeds the chain exact zeros the whole time,
and its recursive states (reverb combs, echo feedback, the biquads, the
loudness EMA, the STFT magnitudes) decay into subnormal floats. On x86 an
operation on a subnormal can cost a microcode assist. The bench
`a_long_mute_costs_at_most_twice_speech_or_a_pause` (ignored in CI; run with `--release`)
puts every bundled preset, loudness on, through the real stage on a thread
that flushes every buffer as the callback does: 10 s of a tone, then 180 s
muted, against a second run that sits 180 s on −70 dBFS room tone after the
tone. The bar: the last 10 s muted costs at most twice the larger of the tone
and the pause's last 10 s. Without the flush, 21 of the 24 presets failed it,
their last 10 s muted costing 2 to 16 times the larger of the two, on the
development PC's i7-14700K (The Oracle 429 µs and Zombie about 1.1 ms per
480-frame buffer).

So the output callback's first statement is `denormals::flush_to_zero()`
(`audio/denormals.rs`), which sets MXCSR's flush-to-zero and
denormals-are-zero bits on the calling thread: it reads MXCSR, ORs in the two
bits and writes it back. cpal owns the output stream's thread, so it is set
every buffer. It applies to everything that thread computes, muted or not.
cpal gives each stream its own thread, so the input and monitor callbacks, like
every other thread, keep gradual underflow
(`flush_to_zero_flushes_this_thread_only`). Off x86-64 it does nothing. With
it all 24 presets passed: per 480-frame buffer, Zombie took 243.3 µs muted
against 277.5 on the tone and 294.8 on the pause, The Oracle 34.1 against 39.0
and 50.2, Clean 11.6 against 3.8 and 11.8 — the last 10 s muted costing 0.68
to 0.99 times the larger of the two. That is one CPU, in a release build;
others weren't measured.

It is `divora-core`'s one production `unsafe`: the workspace sets
`unsafe_code = "warn"`, and this function alone allows it, with a SAFETY note.
The `asm!` block touches only a local and MXCSR, writes MXCSR's other bits back
as it read them, uses no stack and can't unwind. Formally it is undefined
behaviour all the same: Rust assumes gradual underflow (std's `_mm_setcsr`
docs say so of changing DAZ), so a float operation the compiler folds at build
time can still give a subnormal that the same operation at run time would
flush. Nothing on the audio thread gets memory safety from a float, so in
practice that is a difference below 1.2e-38 in a sample.

A first fix fed the starved chain a normal-float floor (±1e-18) instead of
zeros. It didn't help: the noise gate that 23 of the 24 bundled presets start
with took it down 60 dB, to about 1e-21, and loudness's `x * x` average and
the STFT magnitudes squared that below the normal range. It was taken out,
and `feed` writes exact zeros again.

### Who hears what

| Consumer | While muted | Why |
|---|---|---|
| **The send** (the main output: CABLE Input → Discord, OBS, …) | the soundboard, Speak, Critter Chatter and saved Speak clips only. Your voice is exactly zero in `mono` from L samples after the callback first sees the mute. When the output device runs at another rate than the input, the device gets the send through rubato's sinc resampler (`sinc_len` 128), whose history carries the voice about 64 engine-rate samples past that point (worked out from the code: the real-app runs measured the WAV, which is before the resampler) | the gate is before the fold |
| **Monitor** (a separate headphone device) | your voice silent; clips, Speak and previews as the Speak-monitor toggle says | the mic copy is taken after the gate |
| **Single output** (no monitor device) | as the send, plus the monitor-only previews; still gated by Monitor as before | the previews are mixed into `mono` after the gate |
| **WAV recorder** | as the send | its tap is after the fold |
| **Screen takes, their voice stem, Replay** | the voice as zeros, pushed like any buffer; the soundboard as it plays. `.voice.wav` holds voice **and** soundboard | the AV tap is after the gate |
| **Desktop audio** in takes and Replay | unchanged | other apps' sound, not Divora's voice |
| **Voice reading** | Muted, with `mutedInDivora`; the last reading held, nothing analysed | see "The reading" |
| **IN meter** | keeps moving: the raw microphone, so it shows you talking while muted | before everything |
| **OUT meter** | the send: the clips, else zero | after the fold |
| **Reactive envelope** (`modEnv`) | falls to rest | the modulator hears the starved input |
| **Loudness readout** | holds its last gain | below the noise floor the gain is held |
| **Voice-clone reference recording** | still records the raw microphone | a deliberate local recording, tapped in the input callback |
| **Titlebar, Mixer card, spell circle, overlay** | Muted | the store's mirror |
| **Apps that read the microphone** (an OBS mic source, a game's voice chat) | still hear you | Divora can't mute the device |

### The mirror in the store

`UiState.muted` is gone. The store keeps a read-only mirror (`muteState`, and
`muted()` from it) whose only writer is `applyMuteState`. Three things reach
it, in any order: command answers, the boot read, and every `audio-levels`
tick, which carries `inputMuted` and `inputMuteSeq` from one load of the word
(about 30 Hz, engine running or not; `level_update`). `adoptMute` keeps
whichever state has the larger `seq` and drops older ones, so a tick built
just before a command landed, arriving after its answer, changes nothing. (The
overlay controller, v1.55.0, settles the same answer-or-event question by
watching for events while a command is in flight; with a tick always on its
way, the mute needs the number.) A tick without the two fields is no
information, never "unmuted".

**The boot read.** The store sends `input_mute` once, when it is created:
before `App`'s `onMount` enumerates devices with two sync commands that hold
the main thread, so a reload during a hotkey mute shows Muted after one round
trip rather than after the enumeration. Ticks still start after it (the boot
comment in `App.tsx` says why). The boot sends no mute of its own, so a reload
never unmutes the call. `muteKnown` comes true when the read settles (an
answer or a failure), when any state is adopted, or after 500 ms; until the
read lands, the pill shows the push-to-modulate status.

**Labels set, triggers toggle.** A control with a label sends the state its
label names (`setMuted`): the Mixer's Mute / Unmute button, a glyph (its omen,
Mute or Unmute, is read from the same mirror the cast reads) and a MIDI CC.
When the label is stale — the mirror lags a hotkey mute by a tick — a click is
an idempotent no-op whose answer corrects the label, never the opposite of
what it says. A trigger with no label toggles in Rust, so a quick double press
is two flips: the hotkey, and a MIDI pad (`toggle_input_muted`). After a
pointer click (`detail > 0`) the Mixer button gives focus back to the page,
because a focused button takes Space, the in-app push-to-modulate key; from
the keyboard it keeps focus.

**MIDI.** Kind `mute`. The router stays stateless: a note-on calls
`toggleMuted`, a note-off nothing, and every CC goes to the store's `muteCc`
with the mapping's id. The store keeps the side each mapping is on
(`muteCcSides`) and acts only when a CC crosses (`muteCcStep`): rising to 64
or more mutes, falling to 59 or less unmutes, and 60 to 63 keeps the side.
While a mapping's side is unknown — after launch, after the mapping changes,
or after a MIDI input is picked, which forgets every side — a message acts
only if it is 64 or more, and then it mutes. So a fader resting low can't undo
a hotkey mute when touched, and a knob jittering at halfway acts once. The cost: after another surface changed the
mute, a latching CC button's next press does nothing.

**The overlay.** `syncOverlay` sends `overlay:state` through one promise
chain, and sends nothing while `held()` is true; `App.tsx` passes
`() => !app.muteKnown()`. A reload during a mute therefore shows the stream
unmuted (Clean or Modulated) only if the boot read takes more than 500 ms or
fails, and then only until the read or a tick lands. The hold can't freeze the
overlay, because `muteKnown` always comes true. The mute rides
`status: "muted"` as before; `OverlayState` is unchanged.

**On screen.** While muted the titlebar pill is loud and still (`.is-muted`:
the danger colours, a border, bold; nothing animates), and its `title` names
the call, your headphones and recordings. An always-mounted polite live region
beside it says "Your voice is muted." and "Your voice is unmuted." on the
mute's edges only, and nothing until the page has seen a mute. Whether a
screen reader voices it while another app has focus, or while the window is
hidden to the tray, hasn't been checked. With the main window hidden to the
tray, the overlay, when it is open, is the only thing that shows the mute:
there is no tray item or tooltip for it.

### The reading

The reading worker loads the word once a pass (every 20 ms, in
`reading_facts`): `facts.muted` is the device's fact or Divora's mute, and
every store goes through `publish`, which sets `mutedInDivora` when the state
is Muted and Divora's mute is a reason. The state and its cause come from one
load, so they can't disagree. While muted the worker drops what both taps
hold, paired, and holds the last reading as Muted; on each mute edge it drops
the wet window, as it does for a chain change. The panel keys "Muted in
Divora" off `reading.mutedInDivora`, never the mirror: the two travel at
different rates, and joining them flashed "Input silent" after every unmute.
`set_reading_muted` stays the device's fact (still with no caller).

### Threads

- **The output callback:** the flush, one `Acquire` load per buffer, and
  `run`, which moves a `u16`. No allocation, lock or system call.
  `the_voice_stage_allocates_nothing_while_mute_toggles` measures the voice
  stage — an echo, loudness and a clip, with flips that turn a fade round
  mid-way — not the whole callback, where Voice Convert's inference still
  allocates.
- **The main thread:** the three commands and the hotkey's flip, each one
  atomic operation, with no lock. It is a shared queue, though: Tauri runs
  sync commands on the main thread, and global-hotkey handles `WM_HOTKEY`
  there too. A mute pressed or invoked while another sync command holds it —
  a `start_audio_engine` blocked on opening a device — lands when that command
  returns. `Command::Start` tears the old session down first, so no stream
  runs while it waits. (Until v1.57.0 the Speak screen's model downloads and
  voice cloning held it too, for minutes and seconds; see "Long commands off
  the main thread".)
- **The level emitter:** one load per tick, so `inputMuted` and
  `inputMuteSeq` always agree.
- **The reading worker:** one load per pass.
- `AudioEngine::set_input_muted` takes `&self` and no lock, so any thread can
  call it; that is the way in planned for v1.58.0's break timer.

**Latency**, from the press: the main-thread queue (normally empty), then up
to one buffer before the callback reads the word (about 10 ms at 480 frames),
then the fade (5.3 to 8 ms). A Voice Convert overrun adds to it. In the real
app, silence began 0 to 11 ms after each command was sent, at 48 kHz.

    a mute held for minutes in the app (the bench covers its CPU only). Several

## Long commands off the main thread (v1.57.0)

**Why.** Tauri 2 runs a plain sync `#[tauri::command] fn` on the main thread,
start to finish: WebView2 raises `WebResourceRequested` for every IPC request
on its UI thread, and tauri-macros' `body_blocking` calls the function right
there (tauri-macros 2.6.2 `command/wrapper.rs`; wry 0.55.1
`webview2/mod.rs`). That thread is also where global-hotkey's hidden window
gets `WM_HOTKEY` (so every hotkey press, the backend-handled **Mute your
voice** included), where the tray and window events run, where events
emitted from other threads are delivered, and where async commands' answers
are handed to the page. A sync command that takes minutes freezes all of it:
the window can't close to the tray, hotkeys do nothing, and every other
command waits. `async fn` commands, and `#[tauri::command(async)]`, run on
tauri's tokio workers (`async_runtime::spawn`), not the blocking pool, so
blocking work inside them ties up a worker; the shape for long work is
`async fn` + `tauri::async_runtime::spawn_blocking`, as `speak` (v1.27.0)
and the screen-recording commands already were.

**What moved.** The Speak screen's three model downloads
(`download_clone_models` ~157 MB, `download_voxcpm_models` ~1.7 GB,
`download_voxcpm_gpu_model` ~1.2 GB) and voice cloning (`clone_voice`,
`stop_voice_recording`: a whole-file decode and a fresh ONNX session, and
stop's wait for the engine to finalize the WAV). Each is an `async fn` that
claims what it needs, then runs in `spawn_blocking`. Their answers and error
strings are unchanged (`downloading {name}: {e}`).

**Measured** (debug builds, a local server through `DIVORA_MODELS_BASE_URL`
trickling 64 KiB every 100 ms and cutting the connection at 6 of 8 MiB, so
nothing was installed): 1.5 s into `download_clone_models`, a sync
`input_mute` took 9,151 ms with the old build — it answered as the server
cut the connection, 10.6 s in — and the main window didn't answer `WM_NULL`
within 2 s. With this build: 1–2 ms and 5 ms, three times during the
download; a second download was refused in 2 ms; `model_download_status`
read file 1 of 2 at 1, 2 and 3 MiB; the done event carried the kind and the
error, the status read null after, and the `.part` was gone.

**One download at a time.** `AppState.model_download` holds the running
download's latest progress (`None` when idle). `DownloadSlot::try_claim`
refuses a second with `MODEL_DOWNLOAD_BUSY` ("A model download is already
running."); the slot updates the snapshot as bytes arrive and frees it on
drop, so an error, or a panic in a debug build, can't leave it claimed. A
set already on disk answers `Ok` before claiming, with no events. The end of
a download, in order: the blocking task finishes, the slot is freed,
`clone-model-download-done` `{kind, error}` goes out, the command answers —
so a page reacting to the done event can start the next download at once.
`model_download_status` (sync, instant) answers the snapshot, for a page
loaded mid-download: once the main thread is free, F5 is reachable during a
download.

**`download_to_file`.** Takes a `ureq::Agent` and a progress callback (no
`AppHandle`), so it is tested against local HTTP stubs. `model_agent`: 30 s
to connect, 60 s with nothing read (`MODEL_READ_TIMEOUT`) — ureq's default
agent has no read timeout, so a silent server used to hang the download
forever, and with it, before this change, the whole app — and no pooled
connections (`max_idle_connections(0)`): ureq 2 clears a pooled connection's
timeouts and sets the read timeout again only for the body, so from a set's
second file on, the wait for GitHub's redirect and the file's headers had no
timeout at all. The temp file stays `<name>.part`, opened with
`share_mode(0)` on Windows so a second Divora process gets an error instead
of writing into it; any error once it exists removes it, and a body that
doesn't match its `Content-Length` is an error. A process that ends
mid-download (tray Quit doesn't wait for it, nor should it) leaves the
`.part`; `sweep_model_parts` removes the known names at startup (a live one
held by another instance won't delete), and downloading the file again
empties and reuses it. The model file isn't synced to disk before the
rename, as before.

**Voice cloning.** `AppState.voice_clone_busy`, an `AtomicBool` claimed by
`CloneClaim` in the async body before the hand-off and freed when the worker
ends: a second `clone_voice` or `stop_voice_recording` is refused with
"Divora is still making a voice. Try again when it's done.", and so is
`start_voice_recording` (still sync), because the stop's worker reads and
then deletes the fixed `voice-reference.wav` a new take would truncate.
In-page the store's `cloning()` already serialised these; the claim covers a
reload. A recording can now run while the VoxCPM download does, so the
engine a take becomes is decided when it **starts** (`voice_recording_path`
keeps `(path, voxcpm)`), and `start_voice_recording` answers the sentence to
read (VoxCPM) or null, which the page shows for the whole take. Checked at
stop, as before, a take spoken freely became a VoxCPM voice, with the
read-aloud sentence as its transcript, whenever the download finished
during it.

**The page.** One permanent subscription to `clone-model-download` and
`clone-model-download-done`, made when the store is created, replaces the
per-call listener, so a page that didn't start a download still shows it.
At creation the store awaits the done listener, then the progress listener,
and only then reads `model_download_status` (an event emitted before its
listener is registered reaches no one, and a listen answers only once
registered), applying the read only if no event arrived meanwhile (the
v1.55.0 answer-vs-event rule) and never applying a null. The three start
functions keep the page's guard and identity-check their own state, so a
late answer never clears a newer download; the done event refreshes the
status of its kind before clearing, so the button doesn't flash back.

**Left on the main thread, on purpose or for later.** The three shortcut
commands must stay sync: global-hotkey registers on its window's thread, and
the plugin holds its own lock while it runs our handler. Mute, chain edits
and other atomic or channel-send commands stay sync: they are fast and rely
on arriving in order. Deferred, each needing more than a move:
`start_audio_engine` (roughly 150–450 ms; an async Start loses its place in
IPC order, so it needs a two-step split); device enumeration
(`list_audio_*`, `detect_virtual_mic`; about 0.1–0.2 s here, more with many
endpoints; cpal leaves its thread in an STA and owns a process-wide
enumerator, so it needs one long-lived thread); `play_soundboard_clip` on a
cache miss (150–500 ms for a ten-minute file; a later Stop must still win);
`scan_soundboard_folder` (only a network folder is slow); `import_preset`
(only a cloud or network file); `list_speak_clips`.
