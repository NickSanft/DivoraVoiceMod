### Crate responsibilities

| Crate | Purpose | Talks to |
|---|---|---|
| `divora-core` | All non-Tauri-coupled audio logic: capture/output streams (Phase 2), DSP effect trait + implementations (Phase 3+), preset model (Phase 4), soundboard mixer (Phase 5), virtual mic detection (Phase 6). Unit-testable without a UI. | The OS audio APIs (via `cpal`), the filesystem (presets, soundboard cache) |
| `divora-app` | Tauri shell. Owns the IPC surface, lifecycle, window. Bridges UI events to `divora-core` and pushes engine state back. | `divora-core`, Tauri runtime, frontend |

The crate name `divora-app` is internal; the user-visible product name is **DivoraVoice** (set via `tauri.conf.json` `productName`).

### Threading (planned, materializes in Phase 2)

- **Audio callback thread** — driven by `cpal`. Real-time. Zero allocations. Reads input, writes input ring buffer, reads output ring buffer, writes output device.
- **DSP worker thread** — high priority, not real-time. Runs the effect chain + soundboard mixer. Owns mutable DSP state.
- **UI / IPC thread** — Tauri main. Owns presets, settings, device list. Pushes preset changes to the DSP thread via atomic pointer swap.

State across threads:
- Whole-chain swap: atomic pointer to an immutable `Arc<EffectChain>`.
- Per-parameter sweeps: `AtomicF32`/`AtomicU32`.
- Audio samples: `ringbuf` SPSC.

### Internal audio format

- 48 kHz, mono, `f32` samples internally.
- Boundary resampling via `rubato` to match device rates.
- Internal buffer: 256 samples (~5.3 ms at 48 kHz).

### Audio engine architecture

The `AudioEngine` owns a dedicated OS thread (`divora-audio`) that hosts
the cpal streams (which are `!Send`). The Tauri main thread talks to it
through an `mpsc` channel; shared state is an `Arc<EngineState>` with
atomic fields so the UI thread can read levels / monitor / running flag
without locking.

Each cpal callback is **alloc-free**: a stack array up to
`MAX_FRAMES_PER_CALLBACK` (4096 mono samples) absorbs the buffer,
samples flow through a `ringbuf::HeapRb<f32>` SPSC ring buffer between
the input and output callbacks (`RING_BUFFER_FRAMES = 8192` ≈ 170 ms at
48 kHz). The output callback fans the mono signal across the device's
output channels, or writes silence when `monitor` is false.

```
Mic device  -> input callback  -> mono mixdown -> SPSC ring buf
                                      |                  |
                                      v                  v
                              LevelMeter (IN)    output callback
                                                       |
                                                       v
                                  LevelMeter (OUT) -> speaker / headphones
```

#### Constraints (Phase 2 only — relaxed in later phases)

- Sample format: F32 only on both devices. Non-F32 fails with a clear
  `AudioEngineError::UnsupportedSampleFormat`.
- Sample rates must match. `AudioEngineError::SampleRateMismatch` fires
  if not. Resampling via `rubato` lands in Phase 8 polish.
- Internal channel layout: mono. Mixdown is straight sum / channel count.

### DSP architecture

- `EffectChain` is owned by the audio output callback. No locks; no contention with the UI thread.
- The UI sends `DspCommand`s, which `AudioEngine::send_dsp` lowers into `DspEdit`s **on the calling thread** — that is where a chain is built and a voice-model load is started. They travel a bounded SPSC channel, recreated on every engine start, that the callback drains at the top of each buffer.
- `EffectChain::apply(edit)` is the single mutation point, and no **structural** edit through it allocates or frees: a `ReplaceChain` swaps in an already-built chain and **returns** the one it displaced (as does `Clear`), for the per-session graveyard thread to drop. `SetParam` / `SetEnabled` mutate in place.
- The reactive-modulation queue beside it works the same way and for the same reason — with the reactive panel on it is on the preset-switch path too, since a config goes out on every preset switch and every input event of a targeted slider (with the panel off the config is constant and the frontend dedupes it away). It is bounded, and `ReactiveModulator::configure` **swaps** the route tables rather than copying, so the config leaves through the graveyard carrying the table it displaced.
- One free remains **in the drain**: `SetParam` drops the owned key string it was sent, once per slider tick. `divora-core/tests/rt_chain_swap_allocations.rs` asserts it at exactly one — that test drives the real drain functions, not copies of them, and pins the zeros for everything else.
- The soundboard drain takes the same route now: `SoundboardMixer::apply` returns what it retired — a displaced voice's name and decoded clip, or a `Stop`'s own owned name — and the callback pushes it to the graveyard. `play` uses `mem::replace` rather than `*v = Voice { .. }`, which is where the free was: an idle slot still owns an `Arc`, a stopped slot still owns its clip, and when the callback holds a clip's last reference, stealing that slot freed the whole buffer there (measured 3 frees for a 1.9 MB clip, one of them the 1.9 MB). `apply` is `#[must_use]`, and because that only catches an *accidental* discard, a source-level test also pins that the callback routes the value rather than dropping it.
- **`VoiceConvert` inference is the remaining architectural violation, and it is not an allocation problem.** With a model loaded, inference blocks the audio callback well past its deadline: measured on the production path with the bundled model, 23 of 600 callbacks took **83–106 ms** against a 10 ms budget, one every ~260 ms, and the first ~240 ms after a voice lands is silence. The bundled model is the *streaming* export (208-sample chunks), but the downsampler feeding it is built with a 4096-sample output chunk, so a single round hands it ~20 inferences to run back to back. `ort` also allocates tensors per call. (v1.51.1's note said 14–16 ms; that measured `run_inference`, the non-streaming fallback that no longer ships.) Nothing short of moving inference to its own thread behind a latency-compensating queue fixes that, so it is deliberately unfixed and deliberately stated. v1.51.2 moved the *resampling* half off the thread and pinned it; the inference half is untouched, and no test reaches it because CI has no ONNX runtime.
- Engine restarts (Stop → Start) clear the chain; the frontend re-sends `SetChain` via a `createEffect` on `(presetId, engineRunning)`.

### A/B compare flow

```
ui.ab = "A"
chains[presetId]  = live A chain (writable by Inspector + ChainCards)
abSlots[presetId] = { A: snapshot, B: snapshot }

user clicks "B" segmented:
  abSlots[presetId].A := clone(chain())   // snapshot the live edits
  chains[presetId]    := clone(abSlots[presetId].B)
  ui.ab               := "B"
  SetChain(spec)                          // fresh chain to audio thread

user clicks "A":
  abSlots[presetId].B := clone(chain())
  chains[presetId]    := clone(abSlots[presetId].A)
  ui.ab               := "A"
  SetChain(spec)
```

Picking a different preset (`usePreset(id)`) resets `abSlots[id]` to two copies of the new chain and sets `ui.ab` back to A.

### Audio pipeline (Phase 5)

```
mic device ──► input callback ──► mono ring buffer ──┐
                                                     ▼
                                       output callback drains:
                                       1. dsp_rx (effect-chain edits)
                                       2. sb_rx  (play/stop/panic)
                                       3. consumer.pop_slice(&mut mono)
                                       4. chain.process(&mut mono, sr)        ← mic with effects
                                       5. soundboard.mix_into(&mut mono, sr)  ← + clips
                                       6. fan-out to device channels
```

Effects apply only to the voice. Soundboard clips play at their natural amplitude; if they distort the user can reduce levels at the clip source. The virtual-mic routing in Phase 6 will see the combined `mono` so call participants hear *both* the modulated voice and the soundboard.

### Sample-rate handling

Each `Voice` holds the clip's native sample rate. During `mix_into(engine_rate)` the read position advances by `clip_rate / engine_rate` per output sample and adjacent samples are linearly interpolated. This handles common mismatches (44.1 kHz clip on a 48 kHz device) without chipmunking, at the cost of mild aliasing. A proper resampler (rubato) is a future polish job.

### Voice pool

| Field | Purpose |
|---|---|
| `MAX_VOICES = 16` | Hard cap on simultaneous voices |
| `play` | Find an idle voice; if none, steal the one with the lowest `started_at` |
| `stop(clip_id)` | Deactivate every voice with matching id |
| `stop_all` | Mark every voice idle |
| `mix_into(output, engine_rate)` | Add every active voice's interpolated sample to `output`; auto-deactivate at end-of-buffer |
| `snapshot(engine_rate)` | Build a `Vec<PlayingClipSnapshot>` for the UI |

### Cache + commands

The Tauri shell owns the decoded-clip cache (`Mutex<HashMap<String, DecodedClip>>` on `AppState`). `play_soundboard_clip(clipId, path)`:

1. Locks the cache.
2. If `clip_id` is present, clones the `DecodedClip` (cheap — `Arc<Vec<f32>>`) and returns.
3. Otherwise calls `decode_clip(path)`, inserts, returns.
4. Forwards `SoundboardCommand::Play { clip_id, samples, sample_rate }` to the engine.

Subsequent plays of the same clip do zero file I/O.

### VB-Cable detection

Detection is pure name-matching against the cpal device lists — we never open the cable, never poke at the registry. Both heuristics fire case-insensitively:

```
looks_like_cable_input(name)  := "cable input"  ⊂ name  OR  ("vb-audio" ⊂ name AND "input"  ⊂ name)
looks_like_cable_output(name) := "cable output" ⊂ name  OR  ("vb-audio" ⊂ name AND "output" ⊂ name)
```

This recognises:
- Canonical `CABLE Input (VB-Audio Virtual Cable)` / `CABLE Output (…)`
- `VB-Audio Hi-Fi Cable Input` / `VB-Audio Voicemeeter VAIO3 Output`

And rejects unrelated devices (`Blue Yeti X`, `HyperX Cloud II`, `Realtek HD Audio`, etc.).

`detect_virtual_mic()` returns `VirtualMicStatus { detected, cableInputDevice, cableOutputDevice, downloadUrl }` where `detected` is the conjunction of both fields being `Some`. ### Global hotkey architecture

`tauri-plugin-global-shortcut` registers OS-wide hotkeys per Tauri window. The plugin's handler receives `(app_handle, shortcut, event)` and our wrapper looks up the registered id by reverse-mapping `shortcuts: Mutex<HashMap<String, Shortcut>>`, then emits a Tauri event with the canonical payload:

```rust
GlobalShortcutEvent { id, accelerator, state }  // state: "pressed" | "released"
```

Each shortcut id is stable application-defined (`ptm` / `panic` / `monitor`, the reserved prefixes `sb:`, `rec:` and `replay:`); the accelerator is whatever string the user picked (`Space`, `Ctrl+Shift+P`, etc.). The frontend subscribes once in `App.tsx` `onMount` and routes by id in `dispatchGlobalShortcut`, the one JavaScript path every id takes — also while the window is hidden to the tray:

```
event.id         | event.state | action
-----------------|-------------|-------------------------------
"ptm"            | "pressed"   | setUi("pressed", true)
"ptm"            | "released"  | setUi("pressed", false)
"panic"          | "pressed"   | panicSoundboard()
"monitor"        | "pressed"   | toggleMonitor()
"rec:screen"     | "pressed"   | toggleScreenRecording()   (v1.52.0)
"rec:wav"        | "pressed"   | toggleRecording()         (v1.52.0)
"replay:save"    | "pressed"   | saveReplay()              (v1.54.0)
"replay:toggle"  | "pressed"   | toggleReplay() — refused with a toast
                 |             | until Replay has been turned on from
                 |             | the card once                (v1.54.0)
"sb:<clipId>"    | "pressed"   | playTileById(clipId)
```

`syncHotkeyBindings()` is called once after subscribe; it re-registers every persisted accelerator so a Windows restart doesn't lose the bindings (Tauri's plugin loses its registrations when the process exits).

**Persistence (v1.51.4).**

- **What is saved:** the `ptm` / `panic` / `monitor` bindings, in `divora.hotkeyBindings`. Before v1.51.4 the paragraph above was aspirational: these three bindings were held only in memory, so `syncHotkeyBindings()` had nothing to re-register after a restart. ### Why two PTM listeners?

The OS-level hotkey works while the app is unfocused but **does not** swallow the keypress from the focused app. So if a user is typing in Discord with PTM = Space, Discord still gets the spaces. To handle that, `App.tsx` also keeps an in-app `window.addEventListener("keydown")` that triggers the same `ui.pressed` flip when our window has focus AND the event target is `document.body`. Both listeners converge on the same store mutation; the user can't tell which fired.

### Glyph classifier (`src/data/glyphs.ts`)

A deliberately simple geometric classifier — no ML, no template-matching DLLs. Returns `GlyphId | null` (one of triangle / invtriangle / square / circle, or null when the trace is too small / open / unrecognisable).

Pipeline:

```
raw points
  ├─► dedupe              consecutive duplicates removed
  ├─► boundingBox         bail if width < 40 or height < 40
  ├─► resamplePath(48)    uniform arc-length resampling
  ├─► smooth(0)           off by default (natural sampling already smooth enough)
  ├─► endpointGap         classify as "closed" if gap < 0.35 × bbox diagonal
  ├─► turningAngles       cyclic when closed; per-point absolute turn
  └─► findCorners         peaks above ~35°, min separation = N/8, cyclic dedup
```

Decision:

- **0 corners** ⇒ circle
- **4 corners** ⇒ square
- **3 corners** ⇒ triangle vs invtriangle — apex is the corner whose Y is most distant from the median Y of the three corners; apex above the median ⇒ ▲, below ⇒ ▽.
- **anything else** ⇒ null

Tunables live in `CLASSIFIER_DEFAULTS` and are accepted as a partial `config` parameter so tests and future tuning work without forking the module.

### Phase vocoder math (pitch shifter)

```
For each STFT frame at hop H = 256, window N = 1024:

  1. Analysis bin k true frequency:
       expected_advance = 2π · k · H / N
       actual_advance   = phase_now[k] − last_in_phase[k]
       Δ                = wrap_pi(actual_advance − expected_advance)
       true_freq[k]     = (k + Δ · N / (2π · H)) · (sr / N)

  2. Synthesis bin k_out at pitch ratio r = 2^(semitones/12):
       k_src = k_out / r                     (fractional)
       synth_mag[k_out]   = lerp(mag[k_src], mag[k_src+1], frac)
       phase_advance      = (true_freq[k_src] · r) · 2π · H / sr
       synth_phase[k_out] = last_out_phase[k_out] + phase_advance
       last_out_phase[k_out] = synth_phase[k_out]
```

The vocoder maintains its own `last_in_phase` / `last_out_phase` buffers (not the STFT's) so the closure passed to `Stft::process` can mutate them without aliasing the STFT's internal state. Bypass-at-zero-shift means the chain pays zero added latency when the slider is centred.

### Spectrum-warp math (formant shifter)

```
For each STFT frame:

  1. envelope[k]   = mean(mag[k - half .. k + half])     (Hann-style smoother)
  2. excitation[k] = mag[k] / envelope[k]                (clamp env ≥ 1e-6)
  3. warped_env[k] = lerp(envelope[k_src], envelope[k_src+1], frac)
                     where k_src = k / r
  4. new_mag[k]    = warped_env[k] · excitation[k]
```

Phases pass through untouched — formant shifting moves the *shape* of the spectrum, not the per-bin energy across bins. End result: vowel colour darkens / brightens without the fundamental moving.

### Rubato resampler integration

```
                      input_rate = 48 kHz                       output_rate = 44.1 kHz
   ┌──────────┐        ┌──────────────────┐  ┌──────────────────────────┐  ┌──────────┐
   │ Mic      ├───────►│ SPSC ring buffer ├─►│ DSP chain @ input_rate  ├─►│ Resampler│ ──► out
   │ (48 kHz) │        │ (RING_BUFFER_FRAMES)│ │ + Soundboard mix         │  │ (Sinc 128│
   └──────────┘        └──────────────────┘  └──────────────────────────┘  │ tap, B-H │
                                                                            │ window)  │
                                                                            └──────────┘
```

Engine picks `engine_rate = input_rate`. The DSP chain and soundboard mix both run at `engine_rate`. The output callback feeds the chain's mono output into the resampler when needed; if rates match, the resampler is `None` and samples pass through directly.

**One wrapper (v1.51.2).** `dsp::voice_convert` kept a private copy of this wrapper, justified in a comment as avoiding a circular dependency — modules within a crate may reference each other freely, so there was nothing to avoid, and the copy diverged exactly as duplicates do: it kept the fixed-chunk shape and handled the overshoot by discarding it outright. It now uses `MonoResampler`, and its two resamplers are built in `VoiceConverter::new` — i.e. inside `DspEdit::prepare`, on a control thread — rather than lazily from `process`. That moved 1060 allocations, 784 frees and ~0.84 ms out of the audio callback, where a `SetChain` was triggering it after every preset switch, and onto the thread that asked for the switch, taking a chain build with a `VoiceConvert` in it from ~124 µs to ~833 µs.

**Exact fit (v1.51.2).** Each round is sized to the device's own frame count with `Resampler::set_chunk_size`, so one `process` call produces exactly the buffer being filled and nothing is queued between callbacks. `resample_pop` asks the resampler what this buffer needs and pops that much; `resample_render` hands the whole DSP buffer plus a count, so no call site picks a bound. Both are `#[doc(hidden)] pub` for `divora-core/tests/rt_resampler.rs`, whose two-clock harness drives them rather than a copy.

Getting there fixed a badly broken path. A fixed 256-frame chunk against an arbitrary device frame count (480 is the WASAPI shared-mode 10 ms buffer at 48 kHz) overshot on every buffer, and the overshoot was "stashed" by splicing resampler **output** into the **input** queue. The engine also asked for a whole extra chunk every callback, so it demanded more native audio than the input device produces — the ring was permanently empty, the zero-fill ran on 499 of every 500 callbacks, and a third of every block reaching the DSP chain, the recorder, the monitor mix and the voice reading was injected silence. Measured on a 440 Hz tone at 44.1 → 48 kHz with a 480-frame buffer, the tone came out **41 dB below** the noise it was buried in; across the six rate pairs and four buffer sizes the suite covers, the figure ranged from −15 dB to −74 dB. It is now 136–145 dB, and tight across the same grid — the spread collapsing is as much the point as the level.

A small cushion (two rounds, filled once at session start) absorbs the beat between the input device's lump size and the output buffer's — 441 frames arriving every 10 ms against 405 wanted every 9.19 ms, which starves roughly every twelfth callback from an empty ring. The cushion primes and then always serves, which matters only under jitter: with ideal clocks the two designs are indistinguishable (both go silent 2–3 times, all at priming), but with the input device's block size varying by ±120 frames, dropping the latch on every dip measured 9–10 silent buffers over 30 s against 1–2 for priming once. A silent buffer is 10 ms of nothing; serving short instead costs a zero tail of a few frames.

### Latency budget

| Stage | Samples | Time @ 48 kHz |
|---|---|---|
| cpal input buffer | ~256 | 5.3 ms |
| Internal SPSC ring | depends on jitter | ~0–10 ms |
| STFT analysis window | 1024 | 21.3 ms (only when pitch / formant active) |
| Resampler cushion + delay | ~2 rounds + ~64 | ~11 ms (only when rates differ) |
| **Total** | | **~26 ms** (under 30 ms goal) |

The resampler row was "~64 samples, 1.3 ms" until v1.51.2, and that was wrong by four orders of magnitude: the input queue grew without bound — 5.4 s of backlog after 10 s of audio, 32 s after 60 s — so the real figure was unbounded and climbing. The exact-fit rewrite queues nothing; what remains is the priming cushion (two rounds, about 10 ms at 44.1 kHz) plus rubato's own group delay.

Per call to `process(buffer, sample_rate)`:

1. **Bypass paths**: if disabled, off-rate, or `mix < 1e-4`, skip the wet pipeline (the `mix=0` path still drains frames so the model stays warm for a later mix change).
2. **Accumulate** every input sample into `in_queue`.
3. **Drain frames** — while `in_queue.len() ≥ 480`, pop a 480-sample frame, scale to int16-range f32, call `DenoiseState::process_frame`, scale back to ±1, push 480 samples each to `out_queue` and `dry_delay`.
4. **Emit** — for each output slot, pop the head of `out_queue` and `dry_delay` and write `mix * wet + (1-mix) * dry`. When the queues are empty (warm-up), emit silence; the dry signal must NOT pass through during warm-up or the wet stream will audibly repeat those samples on the next call.

### Latency + sample rate

- `RNNoise` is locked to **48 kHz**. Off-rate input bypasses the effect (no allocation, no state drift).
- The wet stream lags the input by `FRAME_SIZE - chunk_size` samples — `max(0, 480 − N)` where `N` is the cpal callback size. For a 256-sample callback that's 224 samples of warm-up silence on the very first frame, then steady-state zero added latency per call (the wet output for *frame K* arrives in the same call that fills *frame K*).
- Wet/dry mix is sample-aligned via `dry_delay` so `mix = 0` outputs the dry stream without re-introducing the warm-up delay; the `mix = 0` shortcut just skips writing wet entirely.

### Why `Denoiser` is a separate effect from `Gate`

- `Gate` is a per-sample hysteresis threshold — surgical "shut up when below −52 dB."
- `Denoiser` is a learned model that suppresses spectral content recognised as noise. It works on the actual *texture* of the signal.
- Stacking gate → denoiser at the head of the chain handles both ends: the gate kills the truly-silent moments, and `RNNoise` cleans the spectrum of what's left. Either alone would either over-process (gate too aggressive) or leave audible breath / fan noise through (denoiser alone).

### Cast spark particles

## Phase 12 — AI voice conversion (ONNX / LLVC)

The `VoiceConvert` effect (`divora-core/src/dsp/voice_convert.rs`) runs an
ONNX voice-conversion model over the mic stream via the `ort` crate
(ONNX Runtime). The reference model is **LLVC** (KoeAI, MIT). It is an
ordinary chain effect (`EffectKind::VoiceConvert`) with one extra seam:
`AudioEffect::install` carries the active model as a `Prepared::VoiceModel`
(numbers go through `set_param`; this carries the things that aren't
numbers). `DspCommand::SetResource` is the matching wire command; the
`VoiceModel` is built — and its ONNX load started — on the control thread,
and the model it displaces is handed back for the graveyard thread to drop,
so no session is ever loaded or freed on the audio thread.

**Graceful degradation is the invariant.** When the ONNX runtime DLL or
the model file is missing, or a model's tensor shapes don't match either
supported contract, the effect falls back to **passthrough** — it never
crashes and never hangs. `onnx_runtime_available()` backs the
Settings → Voice library status banner.

Model I/O, the streaming vs non-streaming contracts, how to produce a
model, and the installer-bundling pipeline are documented in detail in
[`voice-models/README.md`](voice-models/README.md). The streaming export
(threaded cache tensors, ~13 ms chunks) lands in v1.3.0; see the
[CHANGELOG](../CHANGELOG.md).

## Phase 13 — monitor output routing

A **second, independent cpal output stream** so the main send can go to
VB-Cable (→ Discord / games) while you still hear yourself on
headphones. The main output callback runs the DSP + soundboard mix once
and **taps the processed audio into a monitor ring**; the monitor stream
resamples that to its own device rate and plays it (so the soundboard is
audible on the monitor for free — it's mixed in before the tap).

Gating (`main_output_plays`): with a separate monitor device active, the
**main output always plays** (Discord must keep hearing you) and the
Monitor toggle mutes only the headphone stream. With no separate monitor
device, the toggle gates the main output as in Phase 2 — fully
backward-compatible. The monitor device persists to
`localStorage["divora.monitorDevice"]` and is wired into the live
device-switch effect. `StreamInfo` gains `monitorName`;
`start_audio_engine` + `AudioEngine::start` take a monitor argument.

## Phase 14 — live latency readout

`AudioEffect::latency_samples(sample_rate)` (default 0) reports the
algorithmic delay each effect ADDS while actively processing;
`EffectChain::latency_samples` sums the **enabled** effects (they're
serial). Implemented for the effects that buffer:

| Effect | Added latency |
|---|---|
| Voice Convert | the inference chunk — and only when a model is loaded (passthrough adds 0) |
| Denoiser | one 480-sample RNNoise frame (10 ms) — and only at 48 kHz |
| Pitch / Formant | the phase-vocoder STFT window (1024 samples ≈ 21 ms each) |
| Gate / EQ / Robot / Distortion | 0 (sample-by-sample) |
| Echo / Reverb | 0 to dry-path latency (wet tails) |

The engine publishes the chain's added latency (ms) on the ~30 Hz
`audio-levels` event; the Mixer header shows "· +N ms latency" and moves
live as effects toggle. (The originally-sketched buffer-size selector was
dropped — WASAPI shared mode largely ignores requested buffer sizes.)

## Phase 16 — recording

One-click capture of the post-chain output (voice + soundboard) to a

## Stream overlay window (v1.16.0; window fixes v1.51.3)

The overlay is a second `WebviewWindow` labelled `overlay`, created on demand
by the store (`openOverlay` in `src/stores/app.tsx`) and loaded from a second
Vite entry (`overlay.html` → `src/overlay.tsx`, `rollupOptions.input` in
`vite.config.ts`). It renders only the `SpellCircle`. It has no store and no
engine of its own.

### Window

Created with:

- **Frameless and transparent:** `transparent`, `decorations: false`, and
  `shadow: false`. An undecorated transparent window keeps a 1 px border while
  its shadow is on (tauri #8308).
- **On top, not on the taskbar:** `alwaysOnTop`, `skipTaskbar`.
- **Resizable but not maximisable:** `resizable`, `maximizable: false`.
- **Hidden and unfocused:** `visible: false`, `focus: false`.

It is created hidden, placed, then shown. `focus: false` makes tao mark the
window `MARKER_DONT_FOCUS`, so its first show uses `SW_SHOWNOACTIVATE`
(tao `window_state.rs`). Opening the overlay therefore never takes focus from
a game.

### State

- **Main → overlay:** `overlay:state` (`OverlayState`), a broadcast `emit` from
  `syncOverlay` (`src/overlay/sync.ts`) whenever the chain, the status, the
  tweaks or the background mode change while the overlay is open. The overlay
  animates on its own between pushes.
- **Overlay → main:** `overlay:ready` (no payload), emitted once the overlay's
  `overlay:state` listener is registered. Main answers with the current state.
  `tauri://created` fires when the native window exists, which is before the
  overlay's page is listening, so the push sent on open could reach nobody.
  The ready signal is sent right after the listener is registered, not after
  a paint: the window is still hidden while main places it, and a hidden page
  may not run animation frames.
- **The overlay draws nothing until the first state arrives.** Main shows the
  window as soon as it is placed, which can be before the state reaches it,
  and a first frame of the default circle would be captured by OBS.

### Lifecycle

`on_window_event` in `src-tauri/src/lib.rs` turns `CloseRequested` into "hide
to tray" only for `main`, through `hides_on_close(label)`. Until v1.51.3 it did
this for every window. The overlay's `close()` then only hid it, so
`tauri://destroyed` never fired, and the next open found the hidden window and
left it hidden. Now `close()` destroys the overlay, and `tauri://destroyed`
clears `overlayOpen`.

Every path that leaves a visible overlay registers that `tauri://destroyed`
listener and the geometry tracking:

- a new window;
- an existing one being shown again;
- one found still on screen when the store starts.

The last case is a reload of the main page: F5 / Ctrl+R reload a WebView2
page, and the overlay window survives it.

### Geometry

Everything is in **physical pixels**, because Tauri reports monitors,
`outerPosition`, `innerSize`, `onMoved` and `onResized` in physical pixels,
while the `x`/`y`/`width`/`height` a window is created with are logical.

**Saving.** After a move or resize settles (400 ms), main reads the overlay's
`outerPosition` and `innerSize`. It also reads the monitor under the overlay's
centre (`monitorFromPoint`). `currentMonitor()` would not do: it answers for
the window calling it, which is main. All of this is stored in
`divora.overlay` as `{ bg, x, y, w, h, monitor?, scale? }`. Keys the build
doesn't know are carried through. The minimised parking spot (−32000) is
never saved.

**Restoring.** `placeOverlay` (`src/overlay/geometry.ts`) picks the monitor:

1. the monitor saved by name;
2. else the monitor the old rectangle overlaps most;
3. else the primary;
4. else the first monitor.

It then scales the size by the ratio of scale factors, so the window keeps its
apparent size if that display's scaling changed. Finally it clamps the
rectangle fully onto the monitor, with a minimum of 120 px.

Main applies the result by setting the size, then the position, then reading
both back, repeating until they match, at most three times. Windows rescales
a window (`WM_DPICHANGED`) when most of it crosses onto a monitor with a
different scale, and that can happen during the resize as well as during the
move. The target rectangle lies wholly on one monitor, so a second pass has
nothing left to rescale.

### Moving it

A plain left press anywhere that isn't a button starts `startDragging()`
(`src/overlay/drag.ts`). It doesn't use `data-tauri-drag-region`, because
Tauri's drag script toggles maximise on a double-click for any resizable
window (`internal_toggle_maximize` checks `is_resizable` only). That would
blow a transparent, always-on-top window up to the whole screen.

### Permissions

`capabilities/default.json` applies to both windows. v1.51.3 adds
`core:window:allow-set-position` and `core:window:allow-set-size`, so main can
place the overlay. The rest comes from `core:default` or was already granted:
monitor queries, positions and sizes, `is-minimized`, `start-dragging`,
`show`, `close`, and event emit/listen. A separate, narrower capability for
the overlay is planned with the scene editor (see
[`research/stream-studio.md`](research/stream-studio.md)).

### What the overlay never shows

It never shows the voice reading. `src/overlay/state.test.ts` scans every
non-test source file in `src/overlay/` for reading identifiers.

- `sync.test.ts`: drives the real `syncOverlay`, including the ready

### Media Foundation is loaded at run time

`native/mf.rs` loads `mfplat.dll` and `mfreadwrite.dll` with
`LoadLibraryExW(… SYSTEM32)` and resolves every free function it uses with
`GetProcAddress`. The `windows` crate would import them at load time, and on a
Windows N edition without the Media Feature Pack the app would then not start
at all. COM methods are vtable calls and import nothing.
`src-tauri/tests/no_static_media_foundation.rs` reads the built

### The picture

```
WGC (CreateForMonitor, free-threaded pool of 2 BGRA buffers)
  └─ FrameArrived only signals the recording thread
divora-encoder thread (MTA COM, one per take)
  ├─ drain: newest frame → `latest` (BGRA texture), pool buffer returned at once
  ├─ FramePacer: constant-rate PTS (index·10⁷/fps); repeats on a still screen,
  │   counts ticks it fell behind on
  ├─ BGRA → NV12: the D3D11 video processor (BT.709, studio range, scaled to fit
  │   2560×1440, letterboxed if the screen changes shape mid-take) — or, where
  │   the device has no video support, a staging readback and
  │   `nv12::bgra_to_nv12` on the CPU (which stretches a changed shape)
  └─ sink writer (MPEG-4 by attribute, written as `.part`):
      H.264 via the DXGI device manager → hardware encoder where there is one;
      the encoder actually loaded is read back (`GetServiceForStream`)
```

### The sound

The output callback taps two signals where the soundboard is still separate
from the voice — after the chain and loudness, before the fold and before the
monitor-only previews — into preallocated rings, plus one mark per buffer:
cpal's callback instant, the buffer's index, the device frames it wrote, the
input ring's depth before the pop, and the chain's latency. Idle, each
callback does one atomic load. While recording, the output callback reads the
input ring's depth and makes three ring pushes a buffer, and the input
callback takes one timestamp difference and stores the input latency; one
`Instant::now()` per run — on the first buffer of a take, and again after an
engine restart — anchors cpal's instants to the clock the video uses. A buffer that doesn't fit in all three rings is
dropped from all three and counted, so marks and frames can never pair up
wrong. `av_tap.rs`'s tests measure the tap allocation-free (with a live-probe
control) and check that what goes in comes out.

The per-session `divora-av-tap` thread forwards every 5 ms over a bounded
channel. The recorder's sender lives on the engine thread, outside any
session, so a device-loss rebuild — or the user stopping and starting the
engine — hands it to the new session: the take carries on, silent while there
is no engine, and the event's `audioLostAt` says when that began.

`AudioTimeline`, on the recording thread:

1. **Steps.** A buffer well off `ClockFit`'s line (after cancelling scheduling
   jitter with the device frames it wrote) is a stall the call heard too; it is
   kept as silence, not averaged into the clock.
2. **Drops.** A jump in the index is silence of exactly that length.
3. **Placement.** The soundboard at its buffer's time. The voice earlier, by
   input latency + the input ring's depth (smoothed; moved only in a pause, or
   mid-word past 20 ms) + the chain's latency (exact; moves with the chain) —
   so a non-streaming voice model's 256 ms doesn't put the voice a quarter of a
   second behind the picture.
4. **Clock.** `ClockFit` fits engine frames against the video's clock (drift
   held to ±0.5 %), and a Kaiser-windowed sinc reads the mix at the fitted
   positions straight into 48 kHz, so the track neither slides over a long take
   nor depends on the engine's rate.

A sample with no audio is written as silence once it is a second old, so the
track never stalls the file; at the end the timeline waits up to 1.5 s for the
audio to catch up to the last frame.

### Desktop audio (v1.53.0)

What the PC plays, mixed into the same AAC track. Two sources, one loop:

- **Everything except Divora** — *process loopback*
  (`ActivateAudioInterfaceAsync`, `PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE`
  on Divora's own PID): every other process's audio, on whichever device it
  plays, without Divora's voice, soundboard or monitor — or anything Divora
  started — except on a device loopback can't hear: on the development PC,
  the default Realtek USB speakers (which have a vendor virtual mixer) were
  silent to both loopbacks. Whenever another app opens or closes a stream on
  a device, Windows skips about 15 ms of that device's sound and then sends
  30 ms of zeros (measured with a tone playing throughout on the same device;
  endpoint loopback had the tone whole; other devices untested), which the
  timeline counts as a gap.
  Offered only after a trial activation works (and Windows 10 2004,
  `UniversalApiContract` 10, or later).
- **One playback device** — *endpoint loopback*, `device:<id>`: everything
  that device plays, Divora included. Offered where process loopback isn't.

Both are hand-written in `divora-capture` (`native/loopback.rs`) on the same
`windows` 0.61 the crate already uses, and ask Windows for the same thing:
48 kHz float stereo, converted from whatever the device runs at.
`ActivateAudioInterfaceAsync` is resolved at run time like Media Foundation,
so the exe gains no mmdevapi.dll import; its parameters live in a heap blob
owned by the `#[implement]` completion handler — never dropped as a
`PROPVARIANT`, whose `Drop` in windows 0.61 would hand them to
`CoTaskMemFree`.

```
divora-loopback thread (MTA COM; while a stream is open, registered with the
  │  multimedia scheduler's "Audio" task — avrt.dll resolved at run time — or at
  │  HIGHEST priority where that fails)
  desktop_thread::run — open, report, pump, reopen on loss (backoff 1 s → 30 s;
  │  a hung activation is not retried, and says so: the card then shows a
  │  final error, not "trying again"); generic over PacketSource/Opener so
  │  CI drives it with scripted devices; a playback device's first packet
  │  after a quiet wait is marked as a resume (silence before it, not loss)
  ├─ wait ≤ 20 ms on the stream's event; every wake: GetNextPacketSize
  │   (where a dead stream reports), ≤ 64 packets; a playback device that
  │   timed out is asked GetCurrentPadding (an idle device sends nothing);
  │   process loopback that sends no packet for 1 s is treated as lost (on
  │   Windows 11 26200 it sends one every 10 ms, even in silence)
  └─ per packet: packet_time (the packet's QPC on the Instant clock, from one
      anchor pair; arrival − length if flagged or > 1 s off) → DesktopTap::ingest
      (preallocated rings, all or nothing, no allocation — tested) → ReleaseBuffer
recording thread: AudioTrack (track.rs) polls the engine and the desktop,
  pushes both before asking the timeline what is ready
```

In `AudioTimeline` each source has its own lanes (`Lane<C>`, the resampling
half of v1.52.0's epoch, made generic over channels): the engine's epochs as
before, and desktop **runs**. A packet continues the open run only if it
lands within 7.5 ms of the run's line (40 ms for one Windows could not time);
anything else — a lost packet, an idle device coming back, a flagged break, a
reopened device — starts a run on a line of its own, never a step bridged
across the gap. A run's first three packets set where it sits rather than
vote on it, and no resampler starts on a run until they have — or the
recorder, pumping between packets, would glide after a moving line. Every
run that reaches an output frame is summed, so where one
ends and the next begins with nothing lost there is no seam. A frame is
written once each source has delivered it or is overdue (the engine after
1 s, the desktop after 0.25 s — an idle device sends nothing), and only then
is the silence counted.

With desktop audio the track is stereo: the voice and soundboard in the
middle, the desktop at its volume around it, through a soft knee above
−3 dBFS. Without it, the track is v1.52.0's to the bit — pinned by
fingerprints taken from v1.52.0's own code.

Opt-in **stems** (`stems.rs`): `.voice.wav`, and `.desktop.wav` when the take
has desktop audio, 48 kHz float, the very frames the track is mixed from. The
MP4 has no edit list. Over five takes (three short, two of 30 minutes), 79 of
80 soundboard stings were measured at the same sample in its decoded audio as
in the voice stem, and the other one sample apart (in the 30-minute take
before the code review's fixes); on each take the stems were the same length
as the decoded audio, to the sample. Past a WAV file's size limit (about 3.1
hours with desktop audio, 6.2 without) they stop, `stemsError` says where, and
the video goes on.

The **doubling guard** for playback devices (`screen.rs`): what Divora plays
on each device — `send`, `monitor`, `onlyOutput`, `nothing`, `unknown` — from
the engine's routing (`AudioEngine::stream_info`, kept by the engine thread),
matched by device name, the engine's own notion of identity. A device Divora
sends your voice to when a take starts is not recorded. During the take the
desktop feed (`EngineFeed`) reads the engine's routing each time it takes in
desktop audio — every pump, about every 20 ms — and while the recorded device
is one Divora sends your voice to, what it takes in goes in as silence;
`desktopError` says why, updated with the card once a second. The engine
publishes its routing just after its streams start, before a voice could come
back through loopback, so none of it should get in. Measured: with Divora's
output moved onto the recorded device mid-take and back, the device's clicks
(one a second) were left out between the switches and kept before and after,
and Divora's stings there were exactly 0; the switch times are known only to
the second, and that nothing slips through in the first milliseconds is
reasoned, not measured. On the
others the card warns before the take, and `desktopDoubled` reports when the
running engine's monitor switches put Divora's sound there during it.

## Replay (v1.54.0)

The last 15, 30, 60 or 120 seconds of one screen — the picture, the voice and
soundboard as the call hears them, and the desktop audio the card records —
kept in memory and saved as an MP4 on request: from the card, a hotkey or the
tray. Off at every launch: nothing saved turns it on. The first time, only
"Turn Replay on" in the card's explainer turns it on, and the explainer is
needed again if desktop audio is on now but was off when it was read; after
that, the card's switch or the `replay:toggle` hotkey does. Divora writes no
picture or sound to disk until Save. That promise is about Divora: Windows may
still page the ring to its page file, or write it to `hiberfil.sys` when the
PC hibernates. The design, with its review, is in
[`research/stream-studio.md`](research/stream-studio.md) ("As built").

### One pipeline, shared

A take and the ring share **one capture pipeline**: one WGC capture, one
hardware H.264 encoder driven directly, and one audio timeline, on one
`divora-encoder` thread (`divora_capture::spawn_pipeline`). A take started
while Replay is on goes on Replay's pipeline (with Replay's settings, or it is
refused); an arm during a take joins the take's pipeline (on its settings). The
pipeline ends when neither needs it.

```
src-tauri ScreenRecorder (AppState.screen) — Shared, one lock:
  phase/take… (v1.52.0) · slot: Slot<PipelineHandle> (None | Running | Ending)
  · settings: SharedSettings · desktop: DesktopReport · replay: state, seconds,
  saving, last save
    │ PipelineCommand (mpsc + Wake)          ▲ PipelineEvents / TakeEvents
divora-encoder thread (MTA) — Runner (native/pipeline.rs) around PipelineCore:
  ComScope, MfSession (dropped last) · Session { encoder, pool, converter,
  latest, capture, mf_device, gpu } (dropped in that order)
  PipelineCore (pipeline_core.rs, pure): FramePacer · OutputRouter
  (SubmitQueue + KeyframeWatchdog) · EncoderLiveness · AudioTimeline (stems
  on, 600 s fit window) · BlockTail (600 ms) · TakeCore · ReplayRing +
  PendingCut
    ├─ divora-take-mux (one per take): Mp4Writer + StemWriter → rename
    └─ divora-replay-save (one per save): Snapshot → Mp4Writer → rename
```

**The encoder thread writes no recording or clip** (its log lines are its only
file writes): it hands a take's messages and each save to threads of their own
without waiting. Once running, a turn of its loop waits at most 20 ms (2 ms
while a frame waits for the encoder). Its longer stalls:

- the first picture at the start (up to 5 s, before it reports ready);
- a drain (up to 500 ms) when the encoder's last output is wanted — a take
  ending, the screen gone — or a quiesce (up to 100 ms) when it isn't;
- building again: a new encoder and pool after a stream change, new capture
  buffers when the screen changes size, a whole session after a sleep (each
  try a stall of its own; the loop turns between them);
- at the very end, the desktop-audio thread's stop (up to 2 s).

It logs transitions and failures only — every log line is a synchronous file
write. Its encoder's counters go in one line when a session is let go or the
pipeline ends, not when a sleep drops the session or a stream change replaces
the encoder. In a 26-minute armed run (on the build before the review's fixes)
it wrote no line after it began keeping the screen; the only later line in the
log was the save thread's, for the save at minute 5.

**`PipelineCore` makes the pipeline's decisions** about takes, the ring, saves
and faults, and is driven in CI by a pretend encoder, engine and shell. The
Windows shell keeps the timing and a few checks of its own: after a sleep it
tries the rebuild every 2 s for 30 s and makes a new capture after 10 s with no
picture; it asks the graphics device once a second whether it is still there;
it ends a take whose writer can't keep up; and it replaces a frame still
waiting for the encoder with the newer picture. The core's calls that act fill
an `Out` the shell passes in: messages for the open take's writer, clips to
save, what to do with the session — `Drain` (a take ends with nothing else
needing the screen: the border goes, the encoder hands back what it holds),
`Release`, `RebuildEncoder` (the encoder restarted itself), `Rebuild` (after a
sleep) — and whether the thread should end.

### The encoder, driven directly

`EncoderSession` (`native/mft.rs`) drives the hardware H.264 MFT itself
instead of the sink writer: async, D3D11-aware, fed NV12 textures from a pool
of four (`InputPool`, an `IMFVideoSampleAllocatorEx`). It must accept the
pipeline's bitrate (what a take with those settings uses), forced keyframes,
and a GOP of 2 s (set before the output type, read back, refused if the encoder
says otherwise). It asks for CBR, low latency and no B-frames; a refusal of
any of those is logged, in "the direct encoder is ready", and is not fatal.
NVIDIA accepts CBR and low latency and refuses the B-frame count, but makes no
B-frames; any B-frame is caught on the output (DTS ≠ PTS).

A keyframe is forced where a take or a ring segment starts, and whenever a GOP
of input (2 s) has gone by since the frame of the last IDR that came out
(`KeyframeWatchdog`; never while a forced one is still on its way). Outputs
are matched to the frames submitted (`SubmitQueue`) by their timestamps — a
later one means the encoder dropped a frame, none means it re-stamps. An
encoder that stops answering, or stops asking for input, for more than a
second is caught (`EncoderLiveness`).

**An encoder that can't be trusted is remembered until the next launch.**
Re-stamped outputs or B-frames end a take at its last frame and hold the ring.
A forced keyframe more than 3 frames late, or a ring segment that goes more
than two GOPs and 0.1 s without an IDR (`RingFault::NoKeyframe`), holds the
ring ("This PC's encoder doesn't make regular keyframes."); a take already
running carries on. That is said once; later late keyframes are only counted,
and the count is logged in "the pipeline ended" only if the session lasts
until then — not when a ring held for it lets the session go first. After any
of these, no take or arm uses the direct encoder until the next launch. A
stall, a lost device, a stream change or a failed rebuild is not remembered.

**Rung 1 stays.** A take goes through v1.53.0's sink writer on a PC without a
hardware encoder, on a run where the direct encoder failed to build or was
found untrustworthy, and — only for a take started while no pipeline runs —
with `DIVORA_CAPTURE_RUNG1` or `DIVORA_CAPTURE_CPU_CONVERT` set. A take whose
direct encoder fails to build goes on as the same take, with the audio feed it
already opened (`StartError::Direct` hands it back). Any failure of the parts
only the direct path uses — the encoder, its device and input pool, the GPU
colour converter — counts as "failed to build", even when its cause passes
(an encoder whose sessions another app holds): the take falls back, and
Replay is unavailable until the next launch. The capture and the GPU device,
which the sink writer shares, still refuse the take. With Replay on, a take
goes on Replay's pipeline whatever the switches say, or is refused. Replay needs the direct encoder: `replay_support` says why
it can't run — screen recording unsupported, no hardware encoder, or the
direct encoder failed on this run. The switches never stop Replay; they only
get an arm refused (`RUNG1_TAKE`) while a take they sent to the sink writer is
running. `DIVORA_PRETEND_NO_DIRECT` refuses the direct encoder to check that
path.

### Takes on the pipeline

A take starts at the next frame, `k0`, with a keyframe forced there; its file
opens on the first keyframe at or after `k0` (never an earlier one), with that
keyframe's in-band SPS/PPS, or the session's header if it carries none. Its
audio is cut from the shared timeline at
`sample_of(k0) = k0·48000/fps` — exact at 30 and 60 fps — seeded from the last
600 ms of blocks the timeline handed out (`BlockTail`), because with an A/V
offset the timeline runs ahead of the picture. A stop ends the take after the
last frame submitted and waits (≤ 1.5 s) for that frame and its audio; the
take's writer, on its own thread, finishes the file and tells the app —
exactly once, however the take ended. Its audio is sent only as far as its
video has gone, give or take the one 1024-frame block that straddles it, so a
take cut short (an encoder that stalls, a sleep) has less than a block (about
21 ms) of sound past its last frame. A writer 4096 messages or 64 MiB of
encoded video behind ends the take ("The disk couldn't keep up"), its file
kept. The take reports its own counts (frames, drops, the timeline's counters
since it began) and the pipeline's gauges as they are (drift, the voice's
delay).

### The ring

`ReplayRing` (`replay.rs`, pure) keeps access units and the timeline's mixed
track (a PCM ring of `seconds + 4` s, allocated when the ring is made and
again, keeping the newest audio, only when the length changes while Replay is
on):

- **Whole GOPs leave the front**, never single frames, so the front is always
  an IDR: by time while the next IDR is `N` seconds old, and by bytes over the
  cap; the audio under them goes with them. Once full, the ring holds `N` plus
  part of its front GOP: about `[N, N + 2 s)`, a little more when a forced
  keyframe comes late (the test allows `N + 2 s` + 5 frames; the 26-minute run
  at 30 s, on the build before the review's fixes, held 30.1 to 31.95 s).
- **One segment at a time**, one header and one unbroken clock: a header
  change, the engine coming back after a hold, a rebuilt encoder or a sleep
  starts a new one, which clears the ring. A segment's audio is clipped to its
  first frame's sample and seeded from the block tail.
- **Save** cuts the window from the latest IDR at least `N` before the frame
  showing at the press (or the front, if the ring is shorter), pins its first
  GOP against eviction, and waits — never blocking the loop — until the ring
  has that frame and its audio, at most 1.2 s (missing audio is silence). The
  snapshot shares the access units and copies the audio. A save thread checks
  the drive's free space (under 1.1 × the snapshot's size, its video plus raw
  audio: refused, no file written), writes `.part` in time order (audio pieces
  of 100 ms interleaved with the frames, both streams from 0, no edit list;
  throttling off, paced on the writer's queue), renames it, and answers.
  Every Save is answered exactly once (`SaveReply` answers "wasn't saved" if
  dropped), so `replay-saved` goes out once per attempt.
- **Held**: the engine stopped by the user (or its recovery gave up, or it has
  been down 5 s), the screen gone, or the encoder failed: the ring keeps what
  it has, takes nothing new, and a Save still cuts from it; with the engine
  stopped, the timeline's last epoch is closed first, so the soundboard that
  played just before the stop is in the clip. A hold with nothing kept —
  before the first keyframe, or after a sleep emptied the ring (one held for
  the engine waits for it) — turns Replay off, and so does a rebuild that
  fails (the owner's decision: off, where the plan had it held).

**Memory**: `estimate = (N + 2) · bitrate/8 + (N + 4) · 192 kB`, the cap 25 %
over it (what the UI shows, "up to … MB", rounded up), refused past
`min(1 GiB, RAM/8)` (`ullTotalPhys`; shown rounded down). The default — 30 s at
1440p30 Balanced — is up to 81 MB.

### The engine watch and the tap

A device-loss rebuild leaves `is_running()` false for its length, so the ring
can't hold on that: `AudioEngine::user_stop_count()` (divora-core) counts the
user's stops — each Stop, and each Start whose devices won't open — and
`EngineWatch` holds the ring on a count that moved, a recovery that gave up, or
5 s of not running. A device switch in Settings restarts the engine without a
Stop (`restartEngine()`): one that comes back up is a rebuild the ring carries
on through (silence in the gap); one whose devices won't open has already torn
the running session down, counts as a stop, and holds the ring.

**The tap numbers its takes.** A take or an arm waiting for the last pipeline
to end attaches the engine's tap the moment that pipeline lets go of it. When
the output callback had not run in between, it never saw the tap disarmed: it
started no new run, the drain had already dropped the old one, and every
buffer of the new take was thrown away (found in the real app: a take started
right after another had no voice or soundboard). Each attach is now a numbered
take; the callback stamps each buffer with it and starts a run when the number
changes; the drain reads its control messages first, forwards only the
attached take's buffers, drops older ones and keeps newer ones for their
attach. In a debug build of the shipping code, a take started right after
another, and a ring armed right after Replay was turned off, each had 3 of 3
soundboard stings.

### Sleep

`Instant` counts sleep on Windows, so no reading of it from after a sleep may
reach the timeline. Each turn of the loop — the encoder thread's, and the sink
writer's — reads the clock once, then checks for a sleep (`SleepWatch`:
Windows' resume notification, plus the performance counter running ahead of
the interrupt time), and uses that one reading for all its work; only the
wait's length reads the clock live. On a sleep, the moment things end at is
the reading the previous check was given (`sleep::LoopSleep`): from before the
sleep, whether the PC went down in that turn's work or its wait.

Then the feed's contents are thrown away, a take ends at its last frame before
the sleep, its file kept (rung 1 too, through `AudioTrack::finish_at`), a
pending Save is cut there, and the ring's session is rebuilt: at once, again
every 2 s for 30 s, then waiting for a picture for as long as the lock screen
takes, on a new clock. Until that picture, a take is refused ("The screen
isn't sending a picture yet — try again in a moment."), and nothing on the
old clock reaches the timeline: what the feed brings meanwhile is thrown away,
and the first picture starts a new timeline on a new clock. A take's finishing
wait on the sink writer never pumps more than 2 s past its end, so a sleep
during that wait adds at most about a second of silence after the end, never
the sleep.
A ring held for a lost screen or a failed encoder has nothing to keep with
again, so a sleep that empties it turns Replay off; one held for the engine
stays held, empty, until the engine is back.

**None of this has been through a real sleep.** It is covered by tests only:
the pure core given the moment of a sleep, `LoopSleep`, and the bounded
finishing wait.

### The app

`replay.rs` (src-tauri) is the rules, all pure and table-tested:

- the `ReplayState` table: Off → Arming → Armed → Held. A rebuild sends an
  armed ring back to Arming, and so does the engine's return to a ring held
  for it; a ring held for a lost screen or encoder stays held until Replay
  turns off. Whatever would hold a ring still arming turns it off, as do a
  Disarm, Replay turning itself off (a failed rebuild, an emptied hold) and
  the pipeline's end;
- the `Slot` (None / Running / Ending), which tells a take's start or an arm
  to wait while the pipeline is on its way out — up to 3 s (`SLOT_WAIT`),
  then it is refused;
- `SharedSettings` and the refusals in the user's words, `EngineWatch`, the
  memory table, file names (`divora-replay-<date>_<time>.mp4`, from local time
  — the tray saves with no window), the tray view and Quit's wait;
- the wire shapes: `ReplayStatus` with its `ReplayArmed` and `HeldReasonDto`,
  `ReplaySaved`, and `ReplayMemory` with its `ReplayLength`; `ReplayState`
  goes out as its name.

`screen/replay_ops.rs` applies them. `screen.rs` also holds a take's start or
an arm for up to 8 s while a pipeline is still being started (`SPAWN_WAIT`),
then refuses it with "Still stopping the last recording — try again." The
`ended` event detaches the engine's tap before it frees the slot, so a new
pipeline's tap always comes after. A Stop or a Disarm pressed while the
pipeline is still being built is carried out the moment it is ready
(`spawned`), and events from a pipeline that ended before then are not
overwritten by it.

The tray (`lib.rs`) is synced through `run_on_main_thread` (`sync_tray`),
without waiting: the tray's setters block off the main thread, and Quit holds
that thread while it waits. The one exception is Quit's "saving replay…"
tooltip, which `quit_replay` sets directly, already on the main thread. While
Replay is on, the tooltip says so (and with desktop audio) and how the last
save went, the icon gains a red dot, and the menu gains Save replay and Turn
Replay off — never a way to turn Replay on.

Quit waits for a save in progress for as long as its size needs (5 to 60 s,
plus the cut's 1.2 s, worked out again once the clip is cut), then cancels it
and waits up to 10 s more. A save still writing stops within 16 writes, lets
go of its file unfinished and removes the `.part` (retrying for a second while
Windows still holds it). One already finishing its file can't be stopped: it
has the writer's queue to flush — kept to about 4 MiB, but checked only every
16 writes, so up to 16 more can be queued on top — and then the file's index
to write.

The frontend's `armReplay()` is the only caller of `arm_replay_buffer` and
holds the explainer gate, for the card, the `replay:toggle` hotkey and anything
added later: while the explainer is still needed (above), every way but its
"Turn Replay on" is refused with a toast. A length picked while Replay is held
is applied, through it, once the ring runs again. The save toast names the
preset only if the voice was disguised with it from at least 3 s before the
clip began, judged back from the save — or, for a held ring, from when it was
held, where its clip ends. The toast is one always-mounted live region; while
the window is hidden — and WebView2 still says `visible` for a window hidden
to the tray, so it asks the window too — the latest toast waits until the
window is shown.
